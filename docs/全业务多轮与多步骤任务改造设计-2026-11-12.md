# 全业务多轮、多步骤与批量任务改造设计

日期：2026-11-12。状态：实施设计稿；本文不是功能已实现或验收通过的声明。

配套：[功能测评方案与用例](全业务多轮与多步骤任务功能测评方案-2026-11-12.md)。

## 1. 目标、依据和范围

目标是让用户自然描述事情，系统能够跨多轮补充、纠正、选择对象，整理出完整任务，再逐项核对和办理。用户不需要使用“先、再、然后”，也不需要知道接口名称。改造覆盖全部已冻结 MVP 业务，不限定学生账户或排课。

依据仅为以下冻结文件及 AGENTS.md：

- [确定性业务需求](系统需求设计-V2-MVP-v1.0.md)：金额、单价、课程、退款、工资、关账、角色权限。
- [AI 产品需求](系统需求设计-AI-Native-MVP-v1.0.md)：自然语言、多轮上下文、预览确认、候选选择和恢复。
- [技术设计](系统技术设计-AI-Native-MVP-v1.0.md)：Core 独占业务规则和数据；Agent 仅查询、申请预览；浏览器直接确认。

本设计扩展任务组织方式，不增加冻结范围外的业务。自动发微信、实际转账、永久循环排课、工资分批支付等仍然不支持。不得因为某项尚未接入 AI 就将冻结范围内的需求标成“不支持”并验收通过，应标记为待实现。

本文提出的接口、任务状态和页面组件尚待开发。现有代码只用来识别改造位置，不能用作正确业务规则的来源。

## 2. 完整业务清单

每一行均进入同一套多轮、计划、确认和恢复流程。接线清单由实现维护；验收清单独立依据冻结需求维护，两者比较时缺项必须失败。

| 业务 | 需要覆盖的功能 | 多轮或组合示例 | 执行边界 |
|---|---|---|---|
| 学生资料 | 新建、修改、查询、定位学生 | 新建后纠正姓氏，再登记交费 | 建档和已生效资料修改各自确认 |
| 教师资料 | 新建、查询、修改冻结范围内资料、默认工资配置 | 新增老师，补基薪和提成，再查工资 | 资料与薪酬分别按 Core 能力确认 |
| 教师登录账号 | 结构化开通账号、关联与授权范围内账号管理 | 为新老师开通登录 | 密码只由浏览器直达 Core，不进入模型、任务和聊天；没有对应 AI 接口时提供明确的结构化步骤 |
| 课程 | 新建、查询、修改名称、默认单价、时长、启停等已冻结范围 | 新建课程后调整时长，再排课 | 历史课程/消费按冻结规则保持 |
| 课程账户 | 查询余额/单价、交费时开户、明确改价 | 交费并设个性化价，再查流水 | 单独开户不作为新的正常办理入口；历史开户确认单受控恢复 |
| 交费、赠送与流水 | 交费、赠送、查询、支持种类的冲正 | 收款后赠送；错误记录冲正后重登 | 每笔资金独立确认；开户及明确改价与交费在 Core 同事务 |
| 课程安排 | 单节、按周批量、查询、调课、取消 | 排课后更正老师或时间；多位学生分别排课 | 按周批排整体事务；跨对象任务逐项确认 |
| 课消 | 确认上课、店主撤销确认、课消纠错、分组查询 | 确认后查余额；撤销错误确认后纠正 | Core 校验结束时间、扣费、锁价、权限和历史月份 |
| 学籍及欠费 | 查询在读/冻结/退学、欠费和异常 | 查欠费，选人后交费，再查账户 | 不增加直接改余额或任意改学籍入口 |
| 最终退款 | 多课程最终退款、固定手续费、退学 | 查账户后退款，再查回执 | Core 逐课程计算、欠费拦截、清零、记录手续费与退学，整体确认 |
| 工资 | 查询、生成、调整奖扣、支付、撤销支付 | 生成本月工资，补奖金和备注，再登记支付 | 每项写入单独确认；所属月和支付日期独立保存 |
| 手工收支 | 已冻结分类的收入、支出、渠道、备注和查询 | 房租与水电分别登记；更正未确认渠道 | 不能代替学生交费、工资支付或重复登记退款手续费 |
| 经营查询 | 今日概况、目录、流水、课表、课消、工资、现金/经营月报 | 查收入，再查工资，解释结果 | 只引用 Core 数字和来源，不由模型或前端重算 |
| 关账 | 预检、关账、撤销最近关账 | 查预检，解决问题后再关账 | Core 决定是否允许；预检不是授权或永久保证 |
| 回执及结构化入口 | 当前/历史确认单重查、结果定位、人工办理 | 查刚才的回执；模型不可用时继续已生成确认单 | 结果从 Core 重查；业务写入仍经浏览器 |

业务注册项应包含：操作标识、请求/响应生成类型、查询或预览工具、参数说明、对象类型、Core 返回的允许条件/补充要求、结果中的可引用编号、页面组件、可用结构化入口。不在 Agent、Web 或 assistant-protocol 再定义支付渠道、角色等领域枚举。

## 3. 用户行为和产品规则

### 3.1 一句话多个动作

“今天招了一个新生，张小飞，微信缴费2400，并安排一节明天上午9点周老师上的主课”应生成建档、主课交费、单节排课三项。识别“主课”也适用于该笔缴费需要语义判断；若上下文存在多门课且归属不明，只问这一点。

显示完整计划、尚缺信息、将产生哪些记录。信息齐全后用户点击“开始办理”，只生成当前步骤的确认单；不能将开始办理等同于批准全部写入。完成每一步确认后自动准备下一步，用户不必反复输入“继续”。

### 3.2 多轮确定同一件事

| 轮次 | 输入 | 保存后的变化 |
|---|---|---|
| 1 | 今天收了一个叫张娇娇的新生缴费2400元 | 建档和交费草稿；金额2400；发生日期固定为这一轮的今天 |
| 2 | 说错了，姓是王 | 同一个待建学生改为王娇娇，所有引用随之更新 |
| 3 | 缴费通过微信缴费 | 只补渠道，姓名和金额保留 |
| 4 | 缴费是主课，然后单节收费是230元 | 只补课程和单价，不新增另一笔交费 |

信息完整后展示“王娇娇、主课、2400.00元、微信、单节230.00元、明确发生日期”。建档、交费分别确认。单价不必强制由用户提供：没有明确指定时由 Core 取得有效账户单价或课程默认价，并在确认单说明；不能由模型猜价。用户明确给了230元时保留为明确改价意图，由 Core 校验并计算。

### 3.3 补充、改正、撤回和另起任务

- 模型区分：新任务、补充当前任务、修改、撤回某字段、删除步骤、取消剩余、插入查询、查询回执、恢复原任务。
- 新任务不得自动继承上个任务的金额、渠道、手续费、退款对象、工资支付月、关账月。
- 临时查询不丢弃未办完计划；保存返回位置，查询后可自然继续。出现两个可修改对象时问“改哪一个”，不按距离猜。
- “不是微信，是现金”“姓是王”是明确纠正，不应错误列为未解决冲突。“微信收款，方式用现金”且语义不明确才追问。
- 已执行步骤不能改草稿伪装修改了业务；必须另建受支持的修改、冲正、撤销或退款步骤并再次确认。没有合法纠错能力时解释限制。

## 4. 识别和检查

### 4.1 每轮处理

```text
加载当前计划与待确认单状态
 → 同一模型理解本轮动作、对象、补充/改正和原话依据
 → 检查输出结构与可修改范围
 → 使用同一供应商同一模型的另一次调用复核动作是否遗漏、添加或误解
 → 对查明的问题最多重新理解一次
 → 程序应用修改、建立对象引用、排序
 → 经授权的 Core 查询/预检核对对象、条件、默认值
 → 保存新版本，展示计划/追问/当前确认单
```

第二次调用是复核环节，不引入第二供应商或多 Agent，也不能证明一定正确。格式错误、复核不一致、模型不可用均保留原计划，不生成新确认单。默认测试不调用真实模型。

模型输出显式保留所有请求项：已识别业务、未知业务、明确否定、候选值和冲突。未知操作用原话描述保存，不能因操作名称不在清单中而整项丢失。只允许执行注册清单中的查询和预览工具。

### 4.2 模型修改格式

输出包含 `baseRevision`、`turnKind`、`subjectChanges`、`stepChanges`、`issues`、`evidence`。修改只能使用有限命令：新增对象/步骤、设置字段、清除字段、修改引用、取消未执行步骤、补充用户选择。禁止任意 JSON 路径修改、SQL、URL 或工具名称。

原话依据保存消息编号及片段位置；程序验证片段确实属于该消息，字段/操作在白名单中，编号来自当前计划或 Core。原话片段存在不等于语义正确：程序不能凭字符串包含证明“230”属于单价。金额归属、否定、姓名局部纠正等由模型理解和复核；歧义进入追问。需要归一化时同时保存原文和归一化结果供核对。

“姓是王”由模型提出完整姓名王娇娇和被修改对象；不按字符数切姓，不假设所有姓名为单姓。多对象或复姓含义不明时要求补全姓名。

### 4.3 正则的范围

生产业务语义不使用正则识别动作、统计步骤、判断否定或要求连接词。正则仅限金额文本、ISO 格式、UUID 等格式检查；语义上的顺序不能由“先”“再”的出现次数决定。既有语义规则从生产入口移除，历史对照测试与新语义验收分开标识；不能降低原有资金或权限断言使其通过。

### 4.4 相对时间

将消息接收时间、`Asia/Shanghai`、原始时间短语及解析后的 UTC 时间一并保存。业务日计算统一使用时区转换，禁止截 UTC ISO 日期。跨午夜、刷新和重启不重新解释旧消息的“今天/明天”。新一轮明确改为“明天”时以新消息接收日期解析。工资所属月、支付日期、查询区间、关账月分字段处理，不互相推断年份。对不确定年份只补问缺失项。

## 5. 任务数据和对象引用

Agent 使用自己的 PostgreSQL，新增向前迁移，不修改已应用迁移和官方 checkpointer 表。

| 数据 | 字段及用途 |
|---|---|
| 计划 | schemaVersion、planId、threadId、actorKey、revision、状态、当前步骤、时间依据、待解决问题 |
| 办理对象 | subjectId、对象种类、用户提供的名称、已选择的 Core ID、来源消息、修改记录；不是完整业务实体 |
| 步骤 | stepId、注册操作、subject 引用、参数、参数来源、依赖步骤、状态、当前预览编号、执行回执引用、批次和行号 |
| 参数 | value/rawText、来源消息/片段、用户明确/上文引用/Core默认来源；缺失与清除分别表示 |
| 修改记录 | revision、runId、messageId、修改前后、原因、受影响步骤、旧预览处置结果 |
| 预览申请 | stepId、commandRevision、稳定 requestId/幂等键、申请中/已取得/结果待查、previewId |

计划状态：收集信息、可开始、办理中、待处理问题、部分完成、全部完成、取消剩余。步骤状态：待补充、等待前置、可办理、申请预览中、等待确认、结果待查、已完成、失败可处理、已取消、结构化办理待回执。后两类不能被统计成成功。

姓名等信息放在 subject 中一份保存；缴费、工资、排课等使用 subjectId 引用。Core ID 只能来自受权查询、用户候选选择或 Core 已执行回执。建档成功后用回执中的 studentId 绑定后续操作，不按姓名重查后自动选一个。同名、搜索或默认取值都不能绕过用户权限。

计划不是全量账本，不保存模型密钥、密码、用户 JWT 或数据库连接串。模型输入复用现有脱敏机制并扩展新结构；复核环节同样脱敏；只发当前必要对象和参数。

## 6. 排序、全业务条件和批量

### 6.1 顺序规则

仅在用户已要求的动作内推导先后；不能为了“把事办成”擅自新增交费、生成工资、撤销支付或重开月份。

| 组合 | 必须如何处理 |
|---|---|
| 新建学生/老师/课程 → 后续使用 | 前一步成功后取得 Core ID；缺少新建指令时询问，不自动建档 |
| 交费 → 赠送/排课 | Core 核对是否有课程账户；缺账户且计划包含交费时等待交费，否则引导补充 |
| 生成工资 → 调整 → 支付 → 查询 | 每项前一步成功后按最新版本生成下一张确认单；支付额只由 Core 计算 |
| 撤销工资支付 → 重登支付 | 原工资 ID、所属月不变；新支付日期和渠道独立；两次确认 |
| 冲正 → 重登交费；撤销课消 → 纠正 | 引用准确原记录及回执；不修改旧流水；合法路径由 Core 决定 |
| 查询 → 写入 → 查询 | 查询结果可选对象但不能当执行许可；后置查询读取执行后的事实 |
| 预检 → 关账 | 预检警告和硬性禁止按 Core 结果区分；确认关账时再检查 |
| 重开 → 历史修改 | 仅支持 Core 允许的最近关账；用户没有要求重开时不能自动插入 |
| 退款 → 新赠送/新排课 | 退款后的退学/账户条件由 Core 判断；不能默认后续允许 |

用户明确顺序与业务前提不一致时，展示原因和建议顺序，用户明确接受后才修改。无明确顺序时，按已请求动作的依赖排序；彼此独立的写入保留描述顺序。顺序影响查询含义时说明“操作前/操作后”，有歧义则询问。查询可用既有工具执行，写入按一个活动确认单推进。

Core 提供/补齐最小化只读准备接口，返回当前对象版本、缺失参数、允许/拒绝原因及必需的业务前置条件。Agent 只消费结果并安排等待关系，不复制冻结、关账、扣费、退款、工资公式。条件未知或查询失败不得谎报“没有账户/没有老师”。

### 6.2 三种批量

| 类型 | 处理 |
|---|---|
| 明确列举多个对象 | 展开成稳定编号的独立行和步骤，各自选择、补参、确认和回执；整体显示完成/失败/未办数量 |
| “所有欠费学生”等筛选集合 | 先受权查询，再固定本次对象集合及数量给用户核对；期间新增对象不自动加入；条件改变需重新查并核对 |
| Core 已有整体批量操作 | 按周排课仍是一项领域操作，明细完整、任一冲突整批不保存；不能拆成多笔绕开规则 |

“张、李各2400”表示两笔；“两人总共2400”不自行平分。“都用微信”作用范围记录为本批明确对象，不能跨任务继承。重复行提示用户选择保留一笔或确实办理两笔，不静默去重，也不能默认重复收款。

跨业务、跨对象逐项办理不是整份计划的数据库事务。某行失败默认暂停，用户可明确跳过该行/取消剩余并复查依赖；有依赖的后续行不能跳过前置执行。取消只影响未执行项，不自动冲正成功项。

建议首版展开上限20项；这是拟新增的交互范围限制，不是既有业务规则。超限保留草稿并要求用户明确分批，不静默截断，不承诺尚未实现的导入入口。按周批排遵守现有 Core 周数限制，不按展开条目计入20项。

## 7. 异常处理

问题保存 code、原话、受影响步骤、可供用户选择的处理和是否阻止新预览。用户可明确删除不支持项；系统不能静默省略或改成备注。

| 问题 | 例子 | 处理 |
|---|---|---|
| 业务不支持 | 建档、交费、自动微信通知、排课 | 保留4项，标出通知不支持；用户明确删除后其余才可开始 |
| 数值冲突 | 同笔交费同时说微信与现金且无明确纠正 | 保存两候选，问一次实际渠道；其余参数保留 |
| 动作冲突 | 要办理交费又说不要交费 | 核对是纠正/取消还是未解决矛盾；未解决前不生成新预览 |
| 选择对象不明 | 两位周老师、“把他改成230” | 问对应对象或金额用途，不替用户猜 |
| 权限不足 | 老师计划内夹带学生退款或全店工资查询 | 标出不可办理；不得查询、显示或泄露受限数据 |
| 数据变化 | 已选工资已支付、月份已关账、排课冲突 | Core 拒绝；当前项待处理，已完成项保留 |
| 不确定执行结果 | 确认响应丢失、状态接口不可用 | 只重查同一预览；不能新建第二笔或标记成功 |
| 模型故障 | 无法解析/复核不通过 | 不应用本轮修改，保留原计划，允许结构化入口或重试 |
| 分页不完整 | 只拿到部分欠费名单 | 标明未完整，补齐查询后才能固定批次，不拿首页当全部 |

已知的不支持、歧义或冲突未解决时，整份计划禁止生成新的写入确认单；只允许有权限且为澄清必需的查询。事先无法知道的 Core 条件每步准备时重新检查，失败后展示准确部分完成状态。

## 8. 预览、修改和确认竞态

每次预览申请之前保存稳定的 stepId + commandRevision + requestId。普通 Run 重试不能生成新幂等键。修改参数后才增加 commandRevision，旧预览作废；过期重做也记录新申请及旧预览关联。先查明旧申请状态再补发，不能丢失预览编号后换键重试。

执行始终由浏览器携带用户登录态直达 Core，公共受限接口使用 JwtAuthGuard + RolesGuard。Agent 仅 READ/PREVIEW Capability。确认必须引用当前展示的预览版本和稳定 Idempotency-Key，Core service 重新检查权限、有效期、资源版本及关账条件。

用户发送改正时：前端立即暂停本会话旧确认按钮；服务端对旧预览做原子失效/状态核对。失效和确认争用同一个 Core 预览锁：

- 失效先完成：旧确认被拒绝，保存更正后重新准备。
- 确认先完成：返回已执行事实；本轮更正转为单独纠错请求或追问，不能谎称改了未执行草稿。
- 结果未知：冻结新预览，重查旧预览。

失效是 Core 的通用服务方法；新公共入口只接受用户登录态，内部入口仅接受最小 Capability/HMAC，两者不混用。删除步骤、切换对象及取消任务都遵守相同处置。修改后使直接/间接依赖项尚未执行预览失效，独立完成项不改。

## 9. 任务存储、重复请求和恢复

复用 Agent 的 dialogue_tasks，新增 schemaVersion/revision 及任务变更、预览申请记录。具体 SQL 以实现迁移为准；新增唯一约束至少覆盖 threadId+runId 修改应用一次、planId+stepId+commandRevision 申请一次。

读取与提交使用短事务；模型和 Core 网络调用全部放事务外。保留现有同会话串行与 Run 租约，保存时同时检查 actorKey、读取的 revision、当前租约 token 和有效期。过期 worker 禁止提交。版本冲突丢弃旧候选重新读取；固定次数仍冲突时显示当前状态，不盲目覆盖。

预览外部请求与 Agent 保存之间没有跨库事务：先持久化申请意图，再以稳定键请求 Core；崩溃恢复先读取该申请/预览。新增最小内部查询必要时按请求键返回同属用户/会话的预览，不能查询其他账号；不可仅靠 Agent 中未保存的 response。

页面刷新/服务重启读取计划和 Core 预览/回执，重建进度。确认成功但继续通知失败时，打开会话或重试继续可恢复；同一回执只推进一次。登录失效停止继续，重新登录后重新核实权限。不同账号的任务绝不互通。

旧任务带版本兼容读取，已有确认单只从 Core 重查，绝不重放已执行步骤。旧格式无法可靠恢复的部分显示原信息和回执，要求用户明确重新整理未完成事项；不能因解析失败默认为空任务丢掉未决资金结果。

## 10. 接口和页面

以下为拟新增/调整，需实现后导出 OpenAPI 并重新生成客户端，不能手写领域 DTO。

| 位置 | 接口/变更 | 行为 |
|---|---|---|
| Core 公共 Gateway | 现有 POST /api/assistant/runs | 保留自然话语入口，新增预期计划版本供修改检测；旧客户端兼容策略需测试 |
| Core 公共 Gateway | POST /api/assistant/tasks/:threadId/continue | 收 previewId、planRevision、clientRequestId；验证当前用户与步骤归属，只通知推进；Agent 重查 Core 回执 |
| Core 公共预览 | 当前预览失效入口 | 原子失效与返回真实状态；供用户改正/取消使用，不能执行资金 |
| Core 内部只读 | 准备信息/按请求键重查预览 | 最少权限，返回 Core 事实、前置条件、补充参数要求或既有预览；没有 Confirm 能力 |
| 任务查询 | 现有任务详情扩展 | 计划、修改摘要、待解决问题、当前及历史预览引用、部分完成情况 |
| assistant-protocol | task-plan 展示块、通用动作和问题块 | 仅非领域的显示数据；领域参数/枚举通过 Core 生成客户端 |
| Web | 计划、批量行、字段变化、问题选择 | 用普通话显示已知和缺少信息；明确总项数/已完成/未办；当前步骤一个确认入口 |

确认按钮仅确认对应 Core 业务；“开始办理/删除通知步骤/选择现金/继续”只是修改或推进计划。后续预览不因用户一次确认而自动执行。

教师密码等字段需显示“通过安全表单填写”；表单直接请求 Core，Agent 只在受权查询中得知完成与否。尚无可靠回执关联时该步骤保持等待结构化办理，不能靠用户说“办好了”标为成功。模型不可用时原有结构化业务页及 Core 确认仍可使用。
