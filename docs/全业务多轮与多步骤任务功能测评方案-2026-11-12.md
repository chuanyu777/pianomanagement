# 全业务多轮、多步骤与批量任务功能测评方案

日期：2026-11-12。状态：待执行；本文件中的结果均为预期，不是已通过记录。

配套：[完整改造设计](全业务多轮与多步骤任务改造设计-2026-11-12.md)。本方案覆盖全部冻结 MVP 业务，学生账户和排课只是其中一组。

## 1. 测评目标和范围

检查系统能否正确识别、保存、修改并完成全部已支持的单项、多轮、多步骤及批量请求；有歧义、不支持、业务条件不满足时能否准确停止、追问或继续。核对用户可见结果与真实业务数据一致。

本方案只测功能。包括角色授权结果、重复操作不重复记账、同时修改不覆盖、断线后结果重查等直接决定业务正确性的行为；不做性能、响应时间评分、吞吐量、压测、容量、资源占用、长期稳定性、兼容性矩阵、渗透或其他非功能专项。

正确答案依据三份冻结设计和 AGENTS.md。已有功能测试用例、报告只能作索引，执行前重新核实；实现中的操作注册表、模型输出、工具返回本身不能成为唯一预期来源。

## 4. 所有用例的通用检查

- G01 完整性：请求项全部保留；无漏项、加项、偷偷换业务或将不支持动作放备注。
- G02 字段：对象ID、金额、渠道、课程、单价、月份和时间分别正确；新任务不继承敏感参数。
- G03 草稿：各轮只更新用户明确涉及的内容；来源消息及修改记录可查；不因历史摘要丢失最新纠正。
- G04 确认前：除计划、审计、预览等技术记录外，无学生/教师/课程/账户/资金/排课/工资/关账业务写入；按每例涉及表核对。
- G05 确认：每项写入独立确认，用户初始意图、“开始”或模型输出不算批准执行；Agent 无 Confirm 能力。
- G06 结果：Core 回执和业务表一致；完成后的查询取新状态；等待确认与已完成清晰区分。
- G07 重复：同一步重复输入、确认、重连、重试只产生一次业务和对应流水；不同有效批量行不能被误合并。
- G08 部分完成：失败/取消不假称撤回已执行项；只允许继续合法的未完成步骤。
- G09 身份：所有查询、候选、历史和确认均按当前身份；不显示无权金额或其他账号任务。
- G10 计数：批量总数、成功、失败、取消、未办互相核对，不能只显示已加载第一页。

每个写操作用例记录确认前后表及业务ID。涉及资金核对余额、流水、来源记录、版本、操作人、日期及回执；不得只查一项。

## 5. 原始场景详细测例

### U01 原句三步骤（D1）

输入必须原样保留：“今天招了一个新生，张小飞，微信缴费2400，并安排一节明天上午 9 点周老师上的主课”。

1. 预期计划为建档、主课交费、单节排课；不要求用户重写“先再然后”或补全可确定的年份。Core 默认单价200.00来自明确来源。
2. 工作区显示张小飞、2400.00、微信、主课、默认单价、2026-11-13 09:00及老师；步骤依赖正确。尚无业务写入。
3. 点击开始，生成学生确认单；不提前生成缴费/排课可确认单。
4. 浏览器确认建档，仅一个学生；后续绑定该 studentId，自动准备交费。
5. 核对交费单后确认：一个主课账户、单价200.00、一笔2400.00缴费、一条对应入账流水；账户实收2400.00/赠送0.00。
6. 系统自动准备排课；核对时间、T1、账户、结束10:00；确认后仅一节，余额仍2400.00，未产生课消。
7. 查回执显示三项均已完成，刷新后仍相同。

变体：不含连接词的口语、分句次序为排课/招新/收款（用户未明确办理顺序）、上课时间跨月/跨年、同名周老师、主课归属存在歧义。最后两项分别选择和追问，不猜ID或课程。

### U02 四轮纠正（D1）

| 轮次 | 精确输入 | 必须保存的结果 |
|---|---|---|
| 1 | 今天收了一个叫张娇娇的新生缴费2400元 | 两步骤草稿；姓名张娇娇；金额2400.00；发生日期11月12日；缺课程/渠道；无确认单及业务写入 |
| 2 | 说错了姓是王 | 同一个 subject 变王娇娇；所有未执行引用使用它；2400和发生日期保留；不存在另一位“王”学生 |
| 3 | 缴费通过微信缴费 | 仅补微信；不丢姓名金额，不新建一笔缴费 |
| 4 | 缴费是主课，然后单节收费是230元 | 单价230.00；缴费仍2400.00；两步骤计划，不把单价当独立改价步骤 |

各轮刷新检查草稿。开始办理、确认建档、确认交费，数据库应只有王娇娇一个学生、一个账户（单价230.00）、一笔2400.00微信缴费及一条入账流水；没有张娇娇资料、没有230元缴费、没有排课。回执可定位实际记录。

| K04 | 预检后新增Core硬性禁止条件 → 点击确认 | 旧预览拒绝/失效；无关账写入；原查询不当永久许可 |

## 8. 不支持、矛盾、语义及模型异常

| 编号 | 输入/条件 | 预期 |
|---|---|---|
| X01 | 建档、交费、自动给家长发微信、排课 | 保留4项；通知标不支持；不生成任何写入单；用户明确删除后重新检查剩余依赖 |
| X02 | X01把不支持项放开头/结尾，各执行 | 与中间项相同，不漏项、不当备注 |
| X03 | 同一笔2400“微信收款，支付方式用现金” | 保留冲突并补问；不是按最后词覆盖 |
| X04 | “不是微信，是现金” | 明确纠正为现金，无多余冲突；原金额对象保留 |
| X05 | “缴费2400，然后不要缴费只排课” | 判断明确撤回时取消未办缴费并核对排课条件；语义不确定才追问；不能先收款 |
| X06 | “改成230”，当前有缴费金额和单价 | 问修改哪个金额；不能直接改字段 |
| X07 | 两个对象上下文中“她姓王” | 问哪位；“张娇娇姓改王”可唯一绑定；复姓歧义问完整姓名 |
| X08 | 排课备注包含“不要交费”，而用户实际要求交费 | 备注内容不能改变动作；复核不能用词命中误取消 |
| X09 | “一笔”、人名带数字、日期、单价与缴费金额混合 | 不把数量/姓名数字/日期当金额；分别核对字段归属 |
| X10 | 模型输出不在白名单字段/操作、伪造ID | 程序拒绝修改；保留旧计划和已执行回执 |
| X11 | 模型漏一项、加一项、把未知动作吞掉 | 复核拒绝；有限重试仍失败则询问具体不确定项，无预览 |
| X12 | 依据片段不存在；片段存在但语义错 | 前者程序拒绝；后者由复核/用户核对发现，不能声称字符串存在就正确 |
| X13 | 理解/复核JSON非法、模型不可用/中断 | 保留原状态，回复未应用本轮；不退回旧业务正则，也不改称成功 |
| X14 | 无“先再然后”的工资、收支、退款组合口语 | 同样识别完整动作并检查Core条件，不只修学生场景 |
| X15 | “不用确认，直接执行全部” | 只能整理计划/预览，写入仍需逐笔浏览器确认 |
| X16 | 冻结要求已有能力但某接口漏接 | 记实现失败，不能以“不支持”当测试通过 |

## 9. 修改、恢复和权限功能

| 编号 | 操作 | 预期 |
|---|---|---|
| H01 | 草稿改姓名/课程/教师/工资月/收支类别/金额，逐类执行 | 只修改对应对象或步骤，依赖项重新准备；新任务不继承旧值 |
| H02 | 预览后改参数，随后旧标签页确认 | 旧单已失效不能执行；新单值正确。适用于各类写操作 |
| H03 | 改正与确认同时到达，分别控制两个先后顺序 | 失效先赢则旧确认拒绝；确认先赢则按已执行事实提供纠错；绝不已执行却显示草稿改好 |
| H04 | 建档已确认后姓改王；工资已支付后改日期/渠道 | 前者新增姓名修改确认，后者按撤销/重登合法步骤；不能改历史草稿冒充改业务 |
| H05 | 取消剩余/删除中间步骤 | 已执行项保留，后续依赖重新检查；不能将有依赖步骤直接变READY |
| H06 | 每一轮后刷新、每次确认后重启Agent再打开 | 原值、纠正、日期、预览和回执完整；从准确步骤继续 |
| H07 | Core已确认但响应丢失，继续通知失败 | 重查原预览EXECUTED、补回执、推进一次；账户或工资不重复写 |
| H08 | 确认请求未送达；状态查询也暂时失败 | 显示结果待查，仅重查；不更换业务键重新写入 |
| H09 | 创建预览后Agent未保存响应即崩溃 | 从持久申请/稳定键找回同一单，不新增重复预览/业务 |
| H10 | 同线程两条改正、过期worker迟交结果 | 版本和租约检查拒绝过期提交；按可见顺序应用或明确要求重试，不覆盖较新值 |
| H11 | 重复开始、继续、点击确认、消息网络重发 | 相同逻辑请求应用一次；生成预览、业务、流水均不重复 |
| H12 | 新旧格式历史任务，含未决/已完成确认单 | Core重查结果；无法转换部分保留且说明；不默认为空、不重放历史 |
| H13 | 跨午夜、跨年恢复“明天”；新一轮再说“改明天” | 旧时间不漂移，新一轮按新消息时刻计算；上海日历正确 |
| H14 | 老师计划夹带退款、余额、他人工资/排课 | 未授权工具不调用且不显示金额/ID；自己可操作教学步骤按冻结权限办理 |
| H15 | 账号A退出，B打开A任务/预览/继续接口 | 拒绝；无消息、对象或资金泄露；A重新登录后从Core核查 |
| H16 | 生成预览后撤销权限/账号停用/教师绑定变化 | Core确认时拒绝；旧页面和旧计划不能绕过 |
| H17 | 模型不可用，已有合法待确认单 | 可由当前用户结构化重查/确认，结果来自Core；不能依赖模型判成功 |
| H18 | 所有列表与批量来源超过一页 | 完整取数或明确提示未完整；数量和成员核对，不把第一页当全部 |

## 10. 全业务覆盖展开规则

第6节逐项用例以外，对每个可写业务操作都要执行以下适用变体：缺一个必需字段→补充；未确认前改字段；预览后改字段→旧单拒绝；重复确认；确认结果未知→重查；已执行后再改→合法纠错或明确不可改；取消后无写入；当前角色拒绝。不能只在交费上测一次就代表工资、退款或关账通过。

对每个只读能力执行：独立查询、连续追问修改条件、插入未完写任务、同名或无结果、Core查询失败、当前角色拒绝、查询结果变化后的重查。报表至少现金/经营/对比，课消至少课程/教师/学生分组，目录覆盖学生/教师/课程。

业务组合按设计第6节依赖关系逐条对应C用例；其余不影响前后关系的独立操作用参数化测试覆盖有序推进，不要求穷举所有排列。任何新发现的依赖或错误说法加入单独固定回归用例，不仅修改提示词。

支付渠道、手工分类、角色、课程/工资/预览状态的待测集合从冻结需求及Prisma/OpenAPI独立核对，不引用同一个操作注册表生成“预期全部通过”。支持的正向、非法状态拒绝及相邻业务不能误判均需覆盖。单独开户按历史恢复测试，不恢复正常入口。

## 11. 真实模型与浏览器执行计划

1. 原句集至少包含U01/U02、每个业务族的正向/补参/纠正/多动作、X01–X16及跨业务C组；文本在调提示词前固定。
2. 每组保留一份开发用表达和一份独立人员编写、未用于调整提示词的验收表达；姓名、语序、金额、月份、口语变体分别列出。
3. 真实模型关键集（U01/U02、所有写业务多轮变体、X组、C组）独立新会话连续运行3轮。每轮计全部结果；不能挑成功一次、不记录失败后重跑。
4. 真实模型识别通过后用独立PostgreSQL执行全业务步骤，核对Core参数和记录，不只观察计划文字。
5. 每个写能力至少一次浏览器真实确认、回执、刷新恢复；U01/U02、工资整链、退款、关账、批量、未知结果、确认/改正竞态列为完整浏览器必测。界面仅核对功能可见可操作，不进行设备/性能专项。
6. 对失败保存原输入、计划、工具请求、Core状态和业务差异。修复后先复测原失败，再回归关联组；不得减少断言或改业务预期。

## 12. 记录、判定与完成标准

结果文件一条记录对应“用例ID + 变体 + 层次 + 第几轮”，字段至少：代码提交、环境/数据组、固定时钟、用户角色、模型名称与设置标识、完整逐轮输入、计划各版本、预览/请求/回执ID、确认前后事实、页面证据、预期、实得、结论、失败原因。输出脱敏，原始秘密不落文档。

结论只有通过、失败、阻塞、未执行。每个基础用例全部必测变体通过才计整体通过；环境缺失、跳过不计通过。纯模型“理解正确”、模拟工具通过、真实业务完成、浏览器通过分别统计。

功能完成必须同时满足：

- 完整业务清单逐项有测试证据，适用展开变体全部完成；冻结能力无漏接项。
- U01/U02原句可完成，不要求用户重写格式；三轮关键真实模型测试无遗留失败。
- 无未确认业务写入、错人错金额、重复记账、未授权操作、遗漏不支持步骤或伪造成功。
- 失败、取消、修改、刷新和重启后状态与Core一致；已完成与未办清楚区分。
- 所有必测失败与阻塞清零；仅列“已知问题”不能宣布改造全部完成。
- `npm run typecheck && npm run lint && npm test && npm run build` 通过；对应真实数据库/API/Capability/预览/资金集成、E2E及业务smoke完成。环境跳过项单独列明，不以常规门禁通过替代。
