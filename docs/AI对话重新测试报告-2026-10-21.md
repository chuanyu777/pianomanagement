## 4. 主要问题

### 4.1 自然语言理解与参数契约

- “后天排课”三次均误判为创建排课，要求学生、课程和老师，而不是查询。
- “查今天王老师的主课，只看待上课”三次均收到参数不完整/不合法。
- 下月课表、含糊范围、部分综合问题返回通用处理失败，缺少可继续的业务补问。
- 教师“我今天有哪些课、哪些结束未确认”没有正确返回授权课表。服务端没有因此放开资金权限，但可用性不达标。

这些问题不能靠逐句加入关键字补丁解决。需要明确读/写动作、日期范围、筛选条件的字段契约、合法值校验和错误分类，再用整组同义句回归。

### 4.2 新编排未覆盖已确认功能

基础资料维护、开户改价、细粒度流水/欠费/冻结/课消/工资/报表，以及手工收支等能力未完整接入；多动作拆分和逐步确认也未完成。回复“不支持”仍按失败记录。

### 4.3 连续任务和对象引用

- 同名小明选择后再说“给他交费”，没有保留已明确的账户身份，又要求重选。
- 未知“这节课”之后补“林悦明天9点的主课”，没有按明确日期锁定唯一课程，而是返回多日候选。
- 多参数补齐、切换任务及部分权限请求仍有失败；不能仅凭某一次“支付宝”补问成功就认为连续对话已解决。
- 更正金额/渠道、旧预览服务端失效及取消后转查询的一部分连续检查已通过，仍不代替完整用例。

### 4.4 Core 工资与报表数据偏差

冻结业务需求规定：

`应发工资 = 基本工资 + 课消提成 + 奖金`

F3：基本工资 2000.00，课消业绩 1000.00、提成 100.00、奖金 100.00，应发应为 **2200.00**，实际为 **2100.00**；实发字段另加奖金，因此不能仅检查实发而忽略应发。

F4：奖金 180.00 未计入应发成本，预期经营利润 **190.00**，当前计算为 **370.00**。应修 Core 工资统一计算口径及依赖报表，再重新建立正确数据，不在 Agent 或前端重算。

阻塞用例：Q10、Q11、B03、W01、W03、W05、W07。B03 是原用例使用 F3 工资数据的前置依赖，不代表“新增教师”本身已经测出工资错误。Q10 的收入口径补问本可单独测试，但完整用例依赖 F4；本批次仍保留为阻塞，不虚报完成。

## 5. 浏览器确认恢复测试

通过真实浏览器对话生成预览，再由浏览器 JWT 直接确认 Core；代理只制造网络故障，不伪造预览或业务回执。没有实际支付或转账。

| 分支 | 页面及数据库实测 |
| --- | --- |
| Core 成功，确认响应丢失 | 通过 GET 恢复原回执；刷新仍显示已执行；实收 500.00→1500.00，赠送仍80.00；当前账户交费/流水各只新增一次 |
| Core 成功，确认响应和 GET 均不可用 | 只显示重查；重查和刷新均不开放确认；实际只新增一次；网络恢复后读取同一回执，未新增确认 |
| 确认请求未送达 Core | 预览仍PENDING，余额和交费/流水零新增；用户重新查询状态后才出现确认；明确确认后只入账一次 |

三轮使用独立新任务，后一轮承接已成功的合成余额，不声称每轮都从500.00开始。最后余额3500.00/80.00，主课账户共4笔交费和5条流水，包含原有500.00交费和80.00赠送。

第一次代理实验发现浏览器会自动重发传输失败的 POST，虽然 Core 幂等保证只记一笔，却不能证明应用做了 GET 恢复。因此校正代理：自动重发只收到503，不再到达 Core。有效实验记录包含2次到代理的尝试、**仅1次转发到 Core**，并核对恢复 GET。

本节不等于 E02 数据库事务内部失败回滚已实测，也不等于 E03/E05 所有业务动作、设备和重复变体全部通过；这些仍列未完整执行。

证据目录：`test-results/ai-retest-browser-20261021/`。有效记录为 `verified-get-recovery.json`、`unknown-before-network-restored.json`、`failed-request-zero-new-write.json`、`final-after-user-recheck-confirm.json`。
`after-dropped-response-refresh.json` 为校正代理前的探索记录，不作为 GET 恢复通过证据。
