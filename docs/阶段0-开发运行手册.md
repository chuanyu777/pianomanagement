# 阶段 0 开发运行手册

本手册覆盖 AI Native MVP 的阶段 0 基础设施和当前已落地的阶段 1/业务链路运行方式。冻结业务需求仍以
`系统需求设计-V2-MVP-v1.0.md` 和 `系统需求设计-AI-Native-MVP-v1.0.md` 为唯一基线，
本手册不新增业务规则。

状态口径：本手册把“代码已存在”“本次已实测”和“待验收”分开记录。没有实测证据的内容不能写成已完成。

## 1. 启动顺序

### 完整 Docker 验收环境

仓库根目录执行以下命令，构建并以 detached 模式启动完整 Compose 环境：

```bash
docker compose config --quiet
npm run docker:up
docker compose ps
```

Compose 包含 Core、Agent Runtime、Web 和两套 PostgreSQL。Core 等待 Core PostgreSQL 健康后执行
`prisma migrate deploy` 并启动；Agent 等待 Agent PostgreSQL 与 Core 健康后执行项目 SQL migration、
LangGraph 官方 `PostgresSaver.setup()`，启动 Run Worker 后再提供服务；Web 使用 Nginx 提供静态页面，并将
`/api/` 转发至 Core。
首次构建需要 npm registry 和 Docker 镜像可访问。`docker compose ps` 中五个服务的状态都应为 `healthy`；
如果仍在 `starting`，稍等后重查，若退出则查看 `docker compose logs --tail=100 <服务名>`。

访问地址：Web `http://localhost:5173`、Core 健康检查 `http://localhost:3000/api/health`、
Swagger `http://localhost:3000/api/docs`、Agent 健康检查 `http://localhost:3100/health`。
本机数据库端口为 Core `5433`、Agent `5434`。Compose 默认使用 `AI_ENABLED=false`，
没有模型密钥也可以启动；不要在 Compose 文件或文档中填写真实密钥。Compose 中的数据库密码、
JWT 与 HMAC 值仅供隔离的本机开发使用，不得复用于共享、预发布或生产环境。

#### 本地 AI 配置

需要在本地试用 AI 工作台时，在项目根目录创建被 Git 忽略的 `.env`：

```dotenv
AI_ENABLED=true
AI_PROVIDER=deepseek
AI_MODEL=deepseek-chat
AI_API_KEY=<your-deepseek-api-key>
```

然后重启 Agent：

```bash
docker compose up -d agent
curl http://localhost:3100/health
curl http://localhost:3000/api/assistant/status
```

第二个接口返回 `"message":"AI 助手已连接"` 后，打开 `http://localhost:5173` 登录，
即可在工作台输入自然语言。AI 只负责查询和生成 Preview；收款、赠送、排课、退费等写入仍须在工作区由用户确认。
`.env` 不得提交，日志和截图也不要包含 API Key。

#### 首次创建店主

店主不通过 Swagger 注册，必须在 Core 容器中显式运行 bootstrap 命令。以下交互输入避免把密码写进命令历史：

```bash
printf '店主用户名: '
IFS= read -r OWNER_BOOTSTRAP_USERNAME
printf '店主密码（输入不回显）: '
IFS= read -rs OWNER_BOOTSTRAP_PASSWORD
printf '\n'
export OWNER_BOOTSTRAP_USERNAME OWNER_BOOTSTRAP_PASSWORD
docker compose exec \
  -e OWNER_BOOTSTRAP_USERNAME \
  -e OWNER_BOOTSTRAP_PASSWORD \
  core npm run auth:bootstrap:owner -w @piano/core-api
unset OWNER_BOOTSTRAP_USERNAME OWNER_BOOTSTRAP_PASSWORD
```

按提示分别输入用户名和至少 12 位密码。命令成功会显示新建账号；用户名已存在时会报冲突，
这通常表示该持久化数据库已经初始化过店主，不要为重试而清空数据卷。

#### Swagger 登录与受限接口测试

1. 打开 `http://localhost:3000/api/docs`，确认文档加载，并在 `Auth` 分组执行
   `POST /api/auth/login`。请求体填入 bootstrap 时创建的用户名和密码。
2. 确认返回 `accessToken`、`tokenType: "Bearer"` 和用户信息；认证失败应统一显示“用户名或密码不正确”。
3. 若 Swagger UI 显示 `Authorize`，输入 `Bearer <accessToken>`（若输入框已自动添加 `Bearer` 前缀，
   则只填 token），然后执行 `GET /api/auth/me`，预期返回店主公开资料。
4. 在 `Teachers`、`Students`、`Courses`、`StudentCourseAccounts` 等分组试用店主受限接口。
   例如先创建学生与课程，再创建学生课程账户；按接口 Schema 提交金额字符串，交费/赠送写入请求需提供
   `Idempotency-Key`。不要对有副作用的接口反复点击 `Execute`，除非是在验证同一幂等键行为。
5. 如果当前 Swagger 页面没有 `Authorize` 按钮，可用 Swagger 的登录响应拿到 token，再用终端调用受限接口：

   ```bash
   IFS= read -rs ACCESS_TOKEN
   printf '\n'
   curl -H "Authorization: Bearer $ACCESS_TOKEN" \
     http://localhost:3000/api/auth/me
   unset ACCESS_TOKEN
   ```

停止容器但保留数据库数据：`npm run docker:down`。需要删除本机测试数据库时才执行
`docker compose down --volumes`；该操作会删除两个 PostgreSQL 数据卷及其中数据。

### 本机 Node.js 开发

在仓库根目录执行：

```bash
npm install
```

首次运行还要创建两个未提交的本地环境文件：

```bash
cp apps/core-api/.env.example apps/core-api/.env
cp apps/agent-runtime/.env.example apps/agent-runtime/.env
```

按第 2 节填写变量。`.env` 不得提交，也不要把私钥、服务密钥、模型密钥或完整连接串粘贴到对话、日志或截图中。

启动两个本地 PostgreSQL 16：

```bash
npm run db:up
```

约定端口：

- Core PostgreSQL：`localhost:5433`
- Agent PostgreSQL：`localhost:5434`

初始化 Core 数据库和 Prisma Client：

```bash
npm run db:generate
npm run db:migrate
```

初始化 Agent Runtime 自己的 Run/Message/Event 业务元数据表（与 LangGraph 官方检查点表分开）：

```bash
npm run agent:db:migrate
```

初始化 Agent 数据库的 LangGraph 检查点表。该步骤必须显式执行一次，不能藏在服务启动钩子中：

```bash
npm run agent:checkpoint:setup
```

该命令使用官方 `@langchain/langgraph-checkpoint-postgres` 的 `PostgresSaver.setup()`，只连接 Agent PostgreSQL（5434），并记录所使用的版本。不得使用自定义 Prisma checkpointer，也不得连接 Core PostgreSQL。

然后按顺序启动服务：

```bash
npm run dev:core
npm run dev:agent
npm run dev:web
```

浏览器只应访问 Web 和 Core 的公共接口，不能直连 Agent Runtime。当前 Core Gateway 已提供
`/api/assistant/runs`、Run Resume 和 SSE Events；Core 为每个 Run 签发短期 Capability，Agent Worker 负责异步执行。
Web 工作台已接通登录、Assistant Run、SSE、工作区和 Preview 确认；结构化页面提供学生、排课和月度报表只读入口。
确认操作仍由浏览器携带用户 JWT 直接调用 Core，Agent 只能查询和申请 Preview。

## 2. 环境变量

本地环境变量分别放在各服务自己的未提交 `.env` 文件中。`.env` 不进 Git，任何生产连接串、私钥、模型密钥都不得写入文档、日志或命令输出。

Core API：

```text
CORE_DATABASE_URL=<local-core-postgres-url-on-5433>
CORE_PORT=3000
AGENT_RUNTIME_URL=http://localhost:3100
AGENT_DATABASE_URL=<same-local-agent-postgres-url-on-5434>
CAPABILITY_SIGNING_PRIVATE_KEY_B64=<base64-encoded-local-ed25519-pkcs8-key>
INTERNAL_SERVICE_SECRET=<same-local-secret-as-agent-minimum-32-chars>
AGENT_REQUEST_TIMEOUT_MS=15000
AGENT_STREAM_IDLE_TIMEOUT_MS=30000
AGENT_STATUS_TIMEOUT_MS=2000
```

Agent Runtime：

```text
AI_ENABLED=false
AI_PROVIDER=<selected-provider>
AI_MODEL=<selected-model>
AI_API_KEY=<local-model-key-not-committed>
AGENT_DATABASE_URL=<local-agent-postgres-url-on-5434>
CORE_INTERNAL_API_URL=http://localhost:3000/api/internal
INTERNAL_SERVICE_SECRET=<same-local-secret-as-core-minimum-32-chars>
AI_REQUEST_TIMEOUT_MS=15000
AI_RUN_TIMEOUT_MS=60000
AI_MAX_STEPS=<small-positive-integer>
AI_MAX_TOOL_CALLS=<small-positive-integer>
AI_MAX_OUTPUT_TOKENS=<small-positive-integer>
AI_TRACING_ENABLED=false
AGENT_WORKER_ENABLED=true
AGENT_WORKER_LEASE_DURATION_MS=30000
AGENT_WORKER_RENEW_INTERVAL_MS=10000
AGENT_WORKER_POLL_INTERVAL_MS=1000
AGENT_WORKER_RECOVERY_BATCH_SIZE=100
```

阶段0默认 `AI_ENABLED=false`，用于无密钥安装、编译、单元测试和结构化降级验证。只有在已选择供应商、配置本地密钥并显式打开开关后，才运行 Live Model 测试；供应商、模型和数据区域仍按技术设计的部署决策确认。

所有变量都必须由对应服务在启动时校验。Core 没有模型密钥；Agent 没有 Core 数据库凭证。
当前 Agent 不读取或验证单独的 `CAPABILITY_VERIFY_PUBLIC_KEY`；服务间使用同一密钥生成带时间戳与 nonce 的 HMAC，并携带 Capability Header，
随后由 Agent 调用的 Core Internal API 验证 Capability 签名、权限及 `threadId/runId`。不要在环境文件中添加一个
文档未实现的公钥变量来掩盖这个边界。

服务间 nonce 由 Core migration `20261019090000_add_internal_request_nonces` 和 Agent migration
`005_internal_request_nonces` 分别创建在各自 PostgreSQL 的 `"InternalRequestNonce"` 与
`agent_runtime.internal_request_nonces` 表中。Core 和 Agent 各自以数据库原子写入抢占收到的 nonce；
同一 nonce 在 10 分钟保留期内只会有一个请求成功。Agent 或 Core 重启不会清空已消费 nonce；
因此重启和多 Agent 实例都不会放大重放窗口。过期记录可在下一次写入时被同一条原子语句复用，索引支持后续清理。

## 3. 生成 OpenAPI Client

Core OpenAPI 导出和类型化 Client 生成链路已经存在，使用顺序如下：

```bash
npm run openapi:export -w @piano/core-api
npm run generate -w @piano/generated-core-client -- \
  --input ../../apps/core-api/openapi.json
```

`apps/core-api/openapi.json` 和 `packages/generated-core-client/src/generated/` 都是生成物，
不手工编辑、不提交。当前规范已包含健康检查、助手 Gateway、业务 Preview/Confirm 以及 Core 领域 API；
新增领域接口后仍需重新导出和生成，不能手写 generated Client。

## 4. 阶段0验证顺序

1. 访问 `GET http://localhost:3000/api/health` 和 `GET http://localhost:3100/health`。Core 进程启动时会由 `PrismaService` 执行 `SELECT 1`，但健康响应本身只表示进程存活，不是独立的数据库健康响应。
2. 访问 `GET http://localhost:3000/api/assistant/status` 和 Web，确认聚合状态真实反映 Core 数据库与 Agent Runtime；依赖异常时应安全降级，不得泄露内部错误或使用演示数据。
3. 通过公开 Gateway 验证 `POST /api/assistant/runs` 返回 `queued`/`running` Run，再订阅
   `GET /api/assistant/runs/:runId/events`；Agent Worker 应领取 Run、续租并写入终态。内部 Agent 路由仍使用
   时间戳 + nonce HMAC 和 Capability Header，Events 先补发持久化历史，再推送本实例事件。
4. 用真实只读工具查询结构化数据；助手只通过 Core Internal API 和短期 Capability 访问。
5. 通过助手生成单节/批量排课、交费、赠送或最终退费 Preview，在 Web 工作区核对后由浏览器调用
   `POST /api/assistant/previews/:previewId/confirm`。Confirm 必须校验 Preview TTL、资源版本、角色和幂等键，
   并返回 Receipt；未确认前不应写入业务数据。
6. 在 LangGraph `interrupt` 处暂停，关闭第一个 `PostgresSaver`，用第二个实例在同一 `threadId` 恢复，并确认只读节点不重复执行。这个测试验证的是 LangGraph 检查点，不等于 HTTP Run/Event 元数据已跨进程恢复。
7. 验证 SSE 编码、事件校验、持久化历史补发、实时事件推送、心跳、终态关闭、客户端断开清理及
   `Last-Event-ID` 补读。实时广播使用进程内有界 Hub，不跨 Agent 实例；MVP 仍应保持单 Agent 实例，
   跨实例重连只能从 PostgreSQL 补读。
8. 从两个 Agent Runtime 实例并发发送同一签名 nonce，确认只有一个请求通过；重启其中一个实例后再次发送同一 nonce
   仍被拒绝。验证 Agent Runtime 没有 Core 数据库凭证，Capability 不包含 `CONFIRM` 或 `EXECUTE` 权限；确认请求必须
   由浏览器带 JWT 调用 Core，而不是由 Agent 调用。

金额、余额、权限和业务结论必须来自 Core 结构化结果；Agent、Web 和模型不得自行重算。

## 6. 故障排查

- 数据库连接失败：确认 `5433` 是 Core、`5434` 是 Agent；检查两个连接变量是否指向对应数据库，禁止交叉使用。
- Prisma 生成或迁移失败：先执行 `npm run db:generate`，再执行 `npm run db:migrate`；不要修改生成目录或已应用迁移。
- Agent Run/Message/Event 表缺失：先执行 `npm run agent:db:migrate`，再执行 `npm run agent:checkpoint:setup`；前者是项目自有 migration，后者只负责官方 LangGraph 检查点表。
- Agent 启动后 LangGraph 无法恢复线程：确认已单独执行 `npm run agent:checkpoint:setup`，且 `AGENT_DATABASE_URL` 指向 5434；不要在应用启动时隐式建表。若 HTTP Run/Event 历史仍在重启后消失，先检查项目自有 migration、Agent 数据库连接和 repository 日志；它与官方检查点表是两套初始化流程。
- 服务鉴权被拒绝：检查两端 `INTERNAL_SERVICE_SECRET` 是否一致、系统时钟是否同步，以及 HMAC 时间戳、nonce、请求路径、请求体、Bearer Capability、`x-assistant-capability` 和 `Last-Event-ID`；这些安全相关头被替换后签名必须失败，同一 nonce 重放也会被拒绝。签名格式变更时 Core 与 Agent 必须同步部署。
- Capability 被拒绝：检查 Core 的签名私钥、`iss/aud`、`threadId/runId` 和过期时间；Capability 最长 5 分钟。当前 Agent 不单独验证公钥，真正的签名和权限校验在 Core Internal API。
- SSE 断线：不要把 token 放进 URL；用支持 Header 的 fetch 携带最后收到的事件 ID 重连。公开 Gateway 会向 Agent
  转发游标并安全转发事件；Agent 可从 PostgreSQL 补读，但实时 Hub 不跨实例，因此当前只能部署单 Agent 实例。
- Run 长时间停在 `running`：检查 Agent Worker 是否启用、Agent DB migration 是否完成，以及 `AGENT_WORKER_*`
  参数是否满足“续租间隔小于租约时长”。Worker 启动会回收过期租约；失去租约的执行不会继续写事件或终态。
- AI 不可用：保持 `AI_ENABLED=false`，使用结构化降级页面；Core 和确定性业务入口必须仍能启动。
- 端口被占用：停止对应本地服务或调整本地开发端口；不要改变双数据库的 5433/5434 约定而不同步配置。

## 7. 阶段0与当前 MVP 验收边界

以下条件用于判断阶段 0 是否退出，以及当前 MVP 是否具备继续做业务验收的基础；阶段 1 已在实施中：

- Core、Agent Runtime、Web 和两个 PostgreSQL 的边界可重复启动；
- `PostgresSaver` 的 `interrupt`、跨实例恢复和只读节点不重复执行通过；
- 一个真实只读工具和一个业务 Preview/Confirm 完成端到端验证；
- SSE 断线重连后，Run、工作区和公开结果可从持久化状态恢复；当前已完成公开 Gateway 转发、Agent 历史补读和
  Worker 异步执行，实时事件仍限定单 Agent 实例；
- Capability 只能访问授权的只读/Preview 工具，不能确认或执行；
- Agent Runtime 无法连接 Core PostgreSQL；
- 通过 typecheck、lint、unit、build 及阶段0集成/隔离测试；
- 审计记录、错误降级和未调用 Live Model 的默认测试结果可核查；
- 公开 JWT/角色鉴权、基础资料接口和 Assistant Gateway Controller 已实现；浏览器真实生产式 E2E 仍需单独验收。
