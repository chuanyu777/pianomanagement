# 琴行管理系统全局测试方案（v2.0 评审稿）

> 更新日期：2026-10-21；状态：待评审，尚未执行本方案。  
> 配套文档：[测试用例](琴行管理系统全局测试用例-v2.0-评审稿.md)。  
> 本次调整目录、标题和说明方式，测试范围、用例编号及业务预期保持不变。

## 1. 测试目的

检查店主和老师能否在本地 Docker 环境中使用全部已确认的 MVP 功能，并完成日常经营操作。

重点确认：

1. 功能可以使用：能够完成建档、交费、排课、确认上课、退款、工资、报表和关账。
2. 金额计算正确：实收余额、赠送余额、流水、退款、工资和报表能够核对一致。
3. 权限限制有效：老师看不到无权查看的数据，也不能执行店主专属操作。
4. 操作过程安全：必须确认的操作不会自动执行，重复点击或断网不会重复记账。
5. 出错后可以继续：AI不可用、网络中断或服务重启后，用户可以查询结果并继续办理业务。

## 2. 测试范围

### 2.1 本次测试的功能

登录和权限、老师/学生/课程资料、课程账户和单价、交费和赠送、排课和课消、学籍、最终退学退款、工资、手工收支、查询报表、关账，以及AI对话、操作预览、确认、历史记录和手动操作页面。

同一项业务分别从AI对话和手动页面操作，检查结果是否一致。每个页面、接口和可点击按钮都要登记，逐项检查是否遗漏测试。

### 2.2 本次不测试的功能

未纳入本期需求的课包、库存、多校区、自动循环排课、线上退款审批、学生家长端、工资分批支付、利润分配及复杂自定义报表。不进行旧系统迁移，也不要求高并发扩容。

### 2.3 测试依据

- [业务需求](系统需求设计-V2-MVP-v1.0.md)：金额、排课、退款、工资、报表和权限规则。
- [AI产品需求](系统需求设计-AI-Native-MVP-v1.0.md)：对话、确认、工作区、历史、多端和AI故障时的处理。
- [技术设计](系统技术设计-AI-Native-MVP-v1.0.md)及项目规约：服务权限、数据保存、事务、时间和部署要求。

发生冲突时按已冻结的业务需求处理；需求尚未明确的内容列入第15节，不直接以现有代码行为作为正确答案。需求与测试编号的详细对照放在附录。

## 3. 测试环境要求

| 项目 | 要求 |
|---|---|
| 部署环境 | 专用本地Docker测试环境，包含Web前端、Core业务服务、Agent服务及各自PostgreSQL数据库 |
| 数据隔离 | 测试库与开发库分开；清理、故障注入和恢复操作仅针对明确指定的测试副本，不删除开发数据卷 |
| 数据库 | 数据保存、事务和同时操作等测试使用真实PostgreSQL，不用假数据库结果代替 |
| AI服务 | 单Agent实例；支持正常启用和关闭AI两种配置，不要求多个实例同时广播消息 |
| 模型调用 | 默认安装、测试和构建不调用真实模型；真实模型测试单独开启并取得授权，仅使用测试数据 |
| 浏览器 | 内置浏览器和外部Chrome分别登录测试，不能假定共享登录状态 |
| 屏幕尺寸 | 桌面1440×900、1366×768，平板1024×768，手机390×844；另外检查缩放和横竖屏 |
| 时间 | 业务时间按北京时间Asia/Shanghai处理，数据库存UTC；测试使用可控制的时间，不修改电脑系统时间 |
| 密钥 | 仅通过环境配置读取，不写入Git、文档、客户端或测试报告 |

还要从一个没有现有测试数据的Docker环境重新安装一次，确认启动过程不依赖开发机中已有的数据或配置。

## 4. 测试数据要求

全部使用专门创建的测试账号和测试业务数据，不需要用户提供真实数据。

| 数据类型 | 至少准备的数据 |
|---|---|
| 账号 | 1个店主、2个老师，分别有自己的课程和学生 |
| 学生 | 同名学生、多课程学生、从未上课学生、欠费学生、冻结学生、退学生 |
| 课程 | 主课60分钟、陪练45分钟；不同默认单价及学生个性化单价 |
| 账户 | 实收和赠送均有余额、余额为零、赠送不足、实收不足形成欠费 |
| 排课 | 待上课、已完成、已取消；相邻和冲突时间；跨日、月末及年末记录 |
| 收付款 | 现金、微信、支付宝、银行卡、其他；“其他”分别有备注和无备注 |
| 工资和月份 | 未生成、未支付、已支付工资；开放月份、已关账月份和跨月支付 |
| 收支和报表 | 全部4种收入、9种支出分类；空月、单条、多条及超过一页的数据 |
| 时间边界 | 课程结束前/正好结束/结束后；31天前/正好31天/超过31天；零点和闰日 |
| 正确金额 | 用例文档F1–F5规定初始金额、操作过程和正确结果，用于逐笔核对 |

每个用例从约定的初始数据开始，不能依赖前一个用例碰巧留下的数据。比较AI与手动操作时，使用相同初始数据的两个独立副本。

正确结果按已确认的业务公式另行算出并审核，不能让被测功能自己计算一个数，再把它当成预期结果。金额计算必须精确，不能使用会产生小数误差的计算方式。

## 5. 功能性测试

| 功能模块 | 主要测试内容 | 通过要求 |
|---|---|---|
| 登录和账号 | 店主/老师登录、退出、密码错误、登录失效、外部浏览器登录 | 身份正确，错误提示清楚，失效后不能继续操作 |
| 基础资料 | 新建和修改老师、学生、课程；同名学生选择 | 资料正确保存，操作指向所选对象，历史记录仍能查看 |
| 课程账户和单价 | 多课程开户、重复开户、个性化单价、修改单价、更换老师 | 账户按学生和课程分开；历史单价不变；换老师不转余额 |
| 交费和赠送 | 分课程登记、渠道、赠送优先、错误冲正 | 两种余额分别正确变化，流水保留，赠送不算现金收入 |
| 排课和课消 | 单节、按周批量、冲突、调课、取消、确认、撤销确认 | 时长和状态正确；调课取消不扣费；确认时按规则扣费 |
| 学籍 | 在读、冻结、退学及31天规则 | 到达时间边界时状态正确，重新完成课程后恢复在读，退学优先 |
| 最终退学退款 | 多课程退款、欠费拦截、赠送清零、手续费、退款渠道 | 按课程处理，退款金额正确，所有余额清零后标记退学 |
| 工资 | 默认配置、月度生成和调整、提成、奖扣、支付及取消支付 | 保存每月配置和金额，赠送扣费不减少业绩，跨月支付统计正确 |
| 手工收支 | 固定分类、金额、日期、渠道和备注 | 分类及校验正确，不能替代学生交费或重复登记退款手续费 |
| 查询和报表 | 余额、流水、课表、课消、业绩、工资、现金和经营报表、欠费/冻结名单 | 查询范围和金额正确，筛选及分页不改变应有合计 |
| 关账 | 关账前检查、关账、撤销最近关账、跨月纠错 | 历史月份不能被改写，纠错可追溯，关账不产生金额 |
| AI对话 | 各业务查询和办理、日期理解、缺参补问、同名选择、连续对话 | 识别业务和对象正确，不猜测金额或对象，不显示无关结果 |
| 操作预览和确认 | 显示操作前后变化、修改/取消预览、最终确认、执行结果 | 未确认不办理；数据变化后旧预览失效；结果与业务记录一致 |
| 历史和操作记录 | 恢复未完成任务、查看已完成结果、打开原记录、删除聊天展示 | 不重复执行，业务及操作记录不因删除聊天而消失 |

### 5.1 每种登记或修改操作都要检查的内容

对创建资料、开户改价、交费、赠送、排课、课消、退款、工资、手工收支和关账分别检查以下项目，不能只挑一个功能代表全部：

- 正常输入可以完成，结果保存正确。
- 必填项缺失或数值非法时，明确提示且不保存错误数据。
- 没有权限、当前状态不允许或月份已关账时，按对应规则拒绝。
- AI发起的操作先预览，用户确认后才办理；返回修改或取消不会记账。
- 余额、单价、权限或关账状态变化后，旧预览不能继续使用。
- 重复点击、重复提交或两人同时操作，不重复记账或破坏数据。
- 中途失败时，相关记录一起撤回，不能只保存一部分。
- 完成后能够查看业务编号、执行人、时间、结果和相关流水。
- 从AI和手动页面分别操作，业务结果相同。

各项操作和通用检查项的编号见用例文档第18节。不适用的项目说明原因；需求未明确的项目记录为待确认，不当作已经通过。

## 6. 业务流程测试

除逐个功能测试外，还要按真实使用顺序，把多个功能连起来操作。每一步都检查页面、保存的数据和资金流水。仅接口测试成功不能代替整条流程完成。

| 流程编号 | 操作步骤 | 预期结果 |
|---|---|---|
| J01 首次营业 | 登录 → 建老师/课程/学生 → 多课程开户及个性价 → 首次排课 → 到结束时间确认 → 查余额/流水/业绩 | 资料、价格、时长、身份、课消及审计连通；同名消歧不误操作 |
| J02 持续收款授课 | 两课程分别交费/赠送 → 全赠送扣费 → 混合扣费 → 欠费 → 补交 → 余额解释及欠费名单 | 两账户不串账；余额与流水一致；补交后欠费提醒更新 |
| J03 价格、老师与纠错 | 旧价确认 → 改价 → 已排未确认课按新价确认 → 换老师授课 → 店主撤销确认 → 再确认 | 历史保存时记录的值不变；余额不转移；老师业绩归属及正反流水正确 |
| J04 单节及批量排课 | 单节 → 时间冲突 → 调课 → 请假取消 → 批量遇中途冲突整批失败 → 改参数重预览 → 批量成功 → 单节调整 | 相邻不冲突、取消释放占用、失败不保存任何一条记录、无额外金额 |
| J05 最终退学 | 多课程余额 → 欠费拦截 → 处理欠费 → 逐课退款预览 → 手续费 → 确认 → 全账户归零/退学 → 查报表 | 退款单/明细/流水/学籍一致；实际退款与手续费现金和经营两类报表无重复 |
| J06 月度核算 | 课消及赠送 → 各类手工收支 → 工资保存时记录的值 → 调当月基薪/提成/奖扣 → 跨月支付 → 取消支付及重登 → 报表对账 | 业绩、应发、实发、经营月份、现金支付月份与渠道分开正确 |
| J07 学籍变化 | 从未上课 → 首开户计时 → 正好31天 → 超过31天 → 冻结后完成课 → 在读；另测最终退款后保持退学 | 时钟推进即可变化；不依赖人工改状态或重启 |
| J08 月结与跨月纠错 | 关账前检查 → 关账 → 各类历史金额写入拒绝 → 当前开放月反向及正确流水/工资调整 → 撤销最近关账 → 尝试重开更早月份 | 旧月不被改写；新月调整可追溯；关账本身零金额 |
| J09 老师工作日 | 老师登录 → 自己待办/课表 → 自己学生必要资料 → 调课/取消/确认 → 自己业绩工资 → 越权尝试 | 同一套界面完成授权工作；所有入口均不泄露他人或资金数据 |
| J10 AI与手动操作、AI故障 | 同一初始数据分别从 AI/结构化完成关键业务 → 关闭模型服务 → 继续查询与人工办理 → 恢复模型 | 业务结果等价；不靠模型才能营业；故障提示与业务结果不混淆 |
| J11 重复、并发与恢复 | 两浏览器争用同一对象 → 重复确认 → 提交中断网 → 重连查状态 → Agent等待补问时重启 → 继续任务 | 不重复记账、不过期执行；历史/SSE/回执一致 |
| J12 全新 Docker 交付 | 空测试卷安装 → 迁移/初始化店主 → 启动 → 完整业务流程 → 重启 → 备份并恢复到独立测试库 → 重跑只读对账 | 可按文档独立启动；数据持久；恢复不是仅生成备份文件 |

J01–J12是这12条流程的编号，详细步骤见用例文档第20节。各流程使用独立测试数据；J10比较AI和手动操作时，使用相同初始数据的两个副本。

## 7. 边界条件和异常输入测试

### 7.1 金额和输入值

检查空值、0、0.01、负数、两位及超过两位小数、非法数字、缺少对象、同名对象、多课程未指定课程等情况。合法范围按冻结需求执行，尚未确认的金额上限、比例精度等见第15节。

### 7.2 时间和状态

- 课程结束前、正好结束、结束后能否确认。
- 相邻排课、完全重叠、部分重叠、一个时间段包含另一个的冲突检查。
- 距上次完成课程正好31天与超过31天的学籍变化。
- 已完成课调课/取消、已取消课确认、重复确认/撤销等不允许的操作。
- 工资已支付、月份已关账等状态下的修改限制。
- 零点、月末、年末和闰日的日期范围及月份归属。
- 空结果、一条记录、多条记录、超过一页时的显示和合计。

### 7.3 AI表达和日期理解

每个业务都测试完整表达、口语或同义表达、缺少信息、同名对象、连续补充、修改参数和切换任务。

日期覆盖过去、当前和未来，以及单日、周、月和日期范围，并用于课表、流水、工资和报表等适用查询。不能只验证“今天”。无法唯一确定的表达应补问；允许默认当前时间的业务按需求处理，不额外要求用户输入日期。

## 8. 权限和安全测试

- 店主可以操作全部授权业务；老师只能查看和处理自己负责的课程、必要的学生教学信息及本人业绩工资。
- 老师不能通过AI、页面、直接接口、历史、记录链接或导出来查看学生资金、其他老师数据或全店报表。
- 未登录、登录过期、凭据被修改时，业务服务拒绝访问，前端给出正确提示。
- AI服务只能查询和申请预览，不能连接业务数据库，也不能代替浏览器确认执行。
- 篡改内部调用凭据、请求内容或重复发送已用凭据时，服务应拒绝。
- 用户资料和业务备注中的指令或脚本仅作为内容处理，不能执行或改变权限。
- 响应、日志、报错、构建文件和Git中不得泄露密码哈希、密钥、完整连接串或敏感调试数据。
- 操作记录包含用户、最终参数、预览版本、确认时间、业务动作、结果和失败重试信息，不记录模型内部思考过程。

## 9. 界面和浏览器兼容性测试

- 桌面菜单名称可辨认，对话区和结果区比例合理，长表格或长姓名不挤坏布局。
- 工作区展示当前任务对应的列表、报表或确认卡片，不残留上次任务和无关摘要。
- 加载中、空结果、未登录、权限不足、业务失败和AI不可用分别给出正确提示。
- 筛选、选择对象、查看明细、返回修改、确认和结果链接逐个检查，不能只是装饰。
- 正常页面清理常驻工程说明；相关风险在办理对应业务时说明。
- 手机能查看金额、手续费、余额变化、不可逆提示和确认按钮，不依赖横向滚动完成关键操作。
- 平板折叠菜单后仍能切换对话和工作区，横竖屏切换不丢输入、不重复提交。
- 键盘可以完成输入、选择、核对和确认；状态不只靠颜色区分，按钮名称说明具体动作。
- 内置浏览器和外部Chrome分别测试登录和关键业务。

## 10. 故障恢复测试

| 故障或异常情况 | 检查内容 |
|---|---|
| AI未启用、超时或不可用 | 今日数据和手动业务页面仍可使用；逐项测试资料、排课、金额、工资、手工收支和关账的人工办理入口 |
| 提交后断网 | 联网后先查询原操作结果；已经成功则显示原结果，不再提交第二笔 |
| 重复提交或两人同时操作 | 只产生合法的一份结果，不重复扣费、支付、退款或占用同一老师时段 |
| 业务保存中途失败 | 单据、余额、流水和状态一起失败，不留下半成品 |
| 预览后业务数据变化 | 拒绝旧确认，重新预览并要求再次确认 |
| Agent重启或任务中断 | 可以恢复历史和待补信息的任务，不重新执行已完成业务 |
| 消息连接中断 | 重连后补回缺失消息，最终结果与业务记录一致 |
| 后台任务执行者失去执行资格 | 旧执行者不能继续写入结果，新执行者恢复时不重复办理 |
| 容器重启 | 账户、流水、任务和执行结果仍然存在 |
| 数据备份恢复 | 恢复到独立测试库后实际查询和核对，不仅检查备份文件是否生成 |

## 11. 性能测试

按两个人日常使用的规模测试，不提出高并发或扩容要求。

记录Docker启动、页面首屏、普通查询、确认操作和模型回复的实际等待时间，以及服务器资源使用情况。重点观察长结果、模型慢响应和两人同时操作时，页面是否卡死、是否影响其他查询及人工办理。

超时和限额按评审后的配置检查；没有实际测量结果时，不写“性能通过”。

## 12. 测试方法

### 12.1 自动化测试和人工检查

| 测试方式 | 主要检查内容 | 保留的结果 |
|---|---|---|
| 代码和接口检查 | 依赖方向、生成接口客户端、金额类型、身份验证和接口兼容 | 检查输出和接口变更记录 |
| 业务规则测试 | 计算公式、扣费顺序、状态限制和期间限制 | 明确输入、独立算出的预期值和实际值 |
| 真实数据库测试 | 数据约束、事务、锁、同时操作和重复提交 | 操作前后记录、行数、版本及金额 |
| AI服务测试 | 业务识别、参数补全、工具调用、权限、预览和任务恢复 | 调用参数、拒绝原因及任务记录 |
| 浏览器自动化测试 | 登录、表单、结果区、预览确认、筛选和操作结果 | 页面检查、截图、请求和业务编号 |
| 完整流程测试 | 第6节的J01–J12 | 每步结果和跨功能金额核对 |
| 人工页面检查 | 排版、文案、可读性、手机操作和真实语言表达 | 页面、身份、屏幕尺寸及发现的问题 |
| 安装和恢复测试 | 空环境安装、初始化、重启、备份和恢复 | 操作命令、环境版本和恢复后核对结果 |

不用真实模型的自动化测试与真实模型测试分别记录。模拟模型返回正确，不能证明真实AI已经可用。真实模型测试记录供应商、模型、配置和用例版本，不记录密钥。

### 12.2 金额和记录核对

每个资金相关用例都要检查：

1. 页面余额等于按该账户全部不可修改流水另行加总的结果。
2. 一节课的赠送扣除加实收扣除等于当时锁定单价，不跨课程扣款。
3. 冲正金额与原操作相等，原记录仍可查看。
4. 成功时相关单据、流水和状态全部存在；失败时不能只保存部分记录。
5. 报表总计与独立准备的业务记录账本一致，不受分页影响。
6. 同一请求只产生一份结果，已关账历史不被后续操作改写。

### 12.3 测试有效性检查

新增自动检查必须先确认它能发现错误，再验证修复后的正确结果。例如用专用错误样本检查能否发现跨课扣款、重复记账、越权和日期偏移。不得修改真实业务数据或已应用的数据库迁移来制造失败。

“需求要求有哪些功能”与“实际页面和接口有哪些功能”分别整理并相互核对，防止只按已经实现的功能写测试，遗漏尚未实现的需求。

|---|---|---|

## 14. 测试通过标准

### 14.1 允许交付本地试用的条件

以下条件必须全部满足：

- 已确认需求中的每条可测试规则都有对应用例。
- 18个已确认验收场景、12条完整业务流程及每项操作的通用检查全部通过。
- 全部P0和P1用例通过。P0包括金额、安全、数据一致性及阻断营业的问题；P1为其余本期需求，同样不能跳过。
- 没有未解决的资金、安全和功能阻断问题；未执行、失败或待确认的项目不能被统计成通过。
- `npm run typecheck`、`npm run lint`、`npm test`、`npm run build`全部通过；涉及数据库、接口、内部权限和资金的集成测试、浏览器测试及主要业务检查也通过。
- 真实AI与AI不可用时的人工操作分别验证。没有真实模型结果时，只能说明“真实模型未验证”，不能宣称AI可试用。
- 内置和外部浏览器、店主和老师、桌面和手机均完成关键操作；空数据、加载、失败和长结果也检查过。
- 全新Docker环境可按说明启动，重启数据不丢，备份已经实际恢复并核对。
- 提供账号初始化、访问地址和停止/重启说明，不公开密码或密钥。

P2仅指本期需求以外的改进建议，不得把未完成的本期功能降级为P2后放行。

### 14.2 测试报告要求

每条结果记录用例编号及参数、代码版本、镜像、初始数据、用户身份、操作入口、浏览器和屏幕、模型配置、预期、实际、状态、证据和问题编号。

状态分为：未执行、通过、失败、阻塞、有理由不适用。尚未确认规则或缺少条件的项目记阻塞，不记通过。

报告分别列出功能完成情况、实际测试通过情况、12条业务流程结果、金额核对差异、待确认事项、发现的问题和修复复测结果。用例数量和脚本通过率不能单独作为交付依据。

生产服务器的备份调度、容量及模型供应商隐私条款单独验收；本地未验证的生产事项明确标注，不将本地结果写成生产结果。
