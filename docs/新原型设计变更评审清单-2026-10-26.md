# 新原型设计变更评审清单（2026-10-26）

> 评审对象：[琴行经营 AI Native 界面原型](https://piano-ai-native-review-20261026.elvenrain2.chatgpt.site)  
> 原型版本：Sites v3，源代码提交 `c6e85f18857ba93096805aa765734553173d512c`  
> 对照基线：`系统需求设计-V2-MVP-v1.0.md`、`系统需求设计-AI-Native-MVP-v1.0.md`、`系统技术设计-AI-Native-MVP-v1.0.md`  
> 本文性质：评审清单，不直接修改三份冻结/评审基线，也不代表原型中的示例数据和交互已实现。

## 1. 结论摘要

新原型确立了一个更清楚的产品形态：系统从“一个三栏 AI 会话页 + 若干降级页面”变为“一个全局业务导航下的四个 AI 协同页面”。四个一级入口为：

1. 工作台；
2. 学生与账户；
3. 排课与课消；
4. 收支与报表。

每个页面采用“对话区 + 结构化工作区”双栏布局，结构化页面不再只是 AI 故障时才出现的降级入口，而是与 AI 长期并存的核对和办理界面。这一方向值得采纳，但不能直接用原型覆盖现有需求：原型还缺少严格确认、执行回执、同名消歧、批量排课、退款/冲正、最近任务、老师视图、移动端等冻结范围内容，并且存在几处与业务规则冲突的示例。

建议结论：

- **业务口径不因界面改版而变化。** 金额账户、赠送优先、老师权限、退款、工资、关账、Preview/Confirm 和浏览器直连 Core 等硬规则全部保留。
- **AI 产品需求需要形成 v1.1 评审稿。** 重点调整产品信息架构、桌面布局、结构化页面定位、会话与页面导航关系、角色化导航和结构化降级要求。
- **技术设计需要形成 v1.1 评审稿。** 重点增加公开读模型 API、四个页面的路由和状态模型、工作区组件协议、角色化路由守卫，以及结构化按钮直达 Preview 的链路。
- **业务需求只建议补两个明确决策。** 一是学生联系电话是否进入 MVP；二是关账阻断项的确定规则。其余原型冲突优先改原型，不改业务基线。

## 2. 本次建议评审的七个决策

| ID | 决策题 | 建议 | 影响文件 |
|---|---|---|---|
| D1 | 桌面端是否从“三栏工作台”改为“全局侧栏 + 页面内双栏” | **同意。** 左侧只承载一级业务导航与账号入口；当前任务、对话和工作区在主区域内组织。 | AI 产品 §5；技术 §13 |
| D2 | 结构化页面是否继续只称为“降级页面” | **否。** 改为“常驻业务工作区，同时承担 AI 降级”。AI 仍是主要发起方式，但页面可直接浏览和办理。 | AI 产品 §2、§5.4、§13.1；技术 §13.4 |
| D3 | 四个页面是否各自维护独立聊天 | **不建议。** 会话按业务任务持久化，不按页面割裂；切换页面只改变当前工作区和建议上下文。 | AI 产品 §6.3、§11；技术 §12、§13.2 |
| D4 | “最近任务/恢复会话”是否从 MVP 删除 | **保留。** 可放入工作台的任务抽屉或侧栏二级区域，不要求占一级导航，但必须支持重开任务和展示最终回执。 | AI 产品 §5、§11、§15；技术 §12.1、§13.1 |
| D5 | 学生手机号是否进入 MVP 数据模型 | **建议增加可选联系电话。** 需同时确定格式、是否唯一、脱敏和老师可见范围；若不同意，则删除原型中的手机号搜索与展示。 | 业务 §4.2；技术 §9、OpenAPI、Prisma |

## 3. 需求设计需要调整的内容

### 3.1 《系统需求设计 AI Native》建议修改

#### P1. 调整产品定位：AI-first，但不是单一 AI 页面

当前 §2、§5.4 容易让人理解为“AI 主页面 + 备用结构化页面”。新原型应明确为：

> 系统采用 AI 与结构化业务工作区协同的产品形态。AI 负责理解意图、补参和解释；结构化工作区负责实时业务浏览、核对、预览、确认、回执以及 AI 不可用时的直接办理。AI 是主要发起入口，但不是唯一入口。

这项修改不降低 AI Native 要求，也不允许结构化页面另写业务规则。

#### P2. 重写 §5.2 桌面端页面结构

将现有“三栏结构”改为：

| 区域 | 新定义 |
|---|---|
| 全局侧栏 | 四个一级业务入口、当前身份、账号/退出入口；最近任务可作为二级入口或抽屉。 |
| 页面主区域 | 每个一级页面包含对话区和结构化工作区；宽屏并列，窄屏切换。 |
| 对话区 | 当前任务的消息、补问、进度、预览摘要和回执摘要。 |
| 结构化工作区 | 与当前任务或当前页面对应的实时业务视图、表单、预览、严格确认和回执。 |

原“左侧任务栏”的最近任务能力不能因为视觉上没有出现而取消，应在原型下一版明确位置。

#### P3. 新增“四个一级页面”的信息架构

建议在 §5 增加结构化页面表：

| 一级页面 | 默认内容 | 至少包含的结构化能力 |
|---|---|---|
| 工作台 | 今日经营概览 | 今日课程、已结束待确认、欠费、冻结、待处理工资、关账提醒、最近业务记录、最近任务。 |
| 学生与账户 | 学生列表和当前学生 | 基本资料、分课程账户、金额流水、交费、赠送、改价、最终退款、可冲正记录。 |
| 排课与课消 | 周课表 | 单节排课、按周批量排课、调课、取消、确认上课、店主撤销确认、冲突展示。 |
| 收支与报表 | 月度经营概览 | 经营与现金双口径、收支流水、工资、关账/重开账。 |

“四个一级页面”是信息架构，不是新的领域边界。跨页面操作仍由同一 Core 业务服务和 Preview/Confirm 机制处理。

#### P4. 明确导航与会话的关系

原型代码目前为四个页面分别保存聊天记录，这会破坏“一个连续业务目标形成一个任务会话”的冻结规则，也会使跨领域任务难以继续。

建议在 §6.3 和 §11 增加：

- 会话归属于任务，不归属于页面；
- 切换一级页面不自动创建新线程，也不清空当前任务；
- 页面可以向对话提供显式的当前工作区上下文，但金额、渠道、手续费、月份等不得因切页自动继承；
- 用户从结构化页面点击“交费”“调课”等动作时，可以创建新任务或继续当前匹配任务，界面必须明确提示；
- URL、刷新和重新登录后应恢复当前路由、任务、工作区和待确认状态；已执行任务只恢复最终回执。

#### P5. 强化“首屏确定性数据先于模型”的要求

现有 §14.2 已有原则，但新原型把它提升为核心体验。建议在 §5.1、§8.1 明确：

- 工作台概览来自 Core 实时读模型，不等待模型欢迎语；
- AI 只解释概览，不生成概览数字；
- 每项提醒必须带来源、时间范围和可处理入口；
- 工作台数字与对应明细必须来自同一查询口径，不能出现概览 6 节、明细 2 节之类不一致。

#### P6. 增加角色化页面与导航验收

新原型只展示店主视角。建议在 §4、§5、§15 增加老师端验收：

- 老师只看到“工作台”“排课与课消”，以及必要的学生教学信息；
- “学生与账户”若对老师开放，必须是去金额化的教学信息视图，不能复用店主账户页；
- “收支与报表”、交费、赠送、退款、冲正、关账入口对老师不可见且服务端不可调用；
- 角色或老师绑定变化后，已打开路由、历史任务和业务链接重新鉴权。

#### P7. 扩充动态工作区组件定义

现有 §9 的组件表不足以覆盖新原型右侧工作区。建议增加：

- `student-detail`：学生资料和当前学籍状态；
- `course-account-detail`：实收、赠送、总余额、当前单价和最近流水；
- `weekly-schedule`：完整周视图、课程状态和冲突；
- `finance-comparison`：经营结果与现金收支双口径；
- `payroll-detail`：业绩、工资构成和支付状态；
- `preclose-checklist`：阻断项、提醒项、来源明细和重新检查；
- `task-history`：最近任务和最终回执恢复。

这些组件是否进入服务端 `WorkspaceDocument` 白名单应由技术设计确定；普通页面组件不必全部通过 SSE 下发。

#### P8. 结构化入口必须能脱离模型完成业务

原型中多个业务按钮只是把固定文本放入聊天并让 AI 继续补参，这不满足 §13.1。建议明确：

- 结构化页面的“交费、赠送、排课、课消、退款、工资、收支、关账”等按钮必须直接打开确定性表单或生成 Core Preview；
- AI 可帮助预填或解释，但模型不可用时仍能填写、预览、确认、查询回执；
- 结构化入口与 AI 入口使用相同 `actionType`、Preview Schema、确认端点和执行回执。

### 3.2 《系统需求设计 V2》建议修改或澄清

#### B1. 学生联系电话（需评审）

原型提供“按姓名或手机号搜索”和脱敏手机号展示，但冻结需求与当前 Prisma 模型没有联系电话字段。若采纳，建议在 §4.2 增加：

- 可选联系电话；
- MVP 不要求唯一，一个家庭可共用号码；
- 保存规范化值，展示按权限脱敏；
- 老师默认不可见完整号码，是否展示脱敏号码由教学必要性另行确认；
- 搜索结果仍需进行同名/同号码消歧。

若不采纳，原型删除手机号搜索和详情展示，不应由前端虚构字段。

#### B2. 关账阻断规则（需评审）

冻结需求只定义关账后的锁定效果，没有定义“哪些检查必须阻止关账”。原型已经把未支付工资作为硬阻断，而当前 AI 读工具仍明确标记“阻断与提示等级尚未定义”。建议在 §9 增加：

**阻断项建议：**

- 月内已结束但仍待确认的课程；
- 有课程业绩但尚未生成工资的老师；
- 已生成但尚未支付的月度工资；
- 退款单与退款流水不一致；
- 金额流水缺少关联、金额不相反或课消金额与锁定单价不一致；
- 月份已经关账，或不满足最近关账/重开限制。

**提醒项建议：**

- 欠费学生、冻结学生等不影响历史金额正确性的经营提醒；
- 月末以后仍存在的未来待上课程；
- 其它需要店主知晓但不会导致报表错误的事项。

关账准备度百分比只能依据服务端返回的固定规则计算；在阻断分级未冻结前，不应展示 `75%` 这类看似确定的结果。

#### B3. 不建议增加“剩余课次”派生口径

原型账户卡的“约可上 2 节”与“按金额账户、不采用剩余课次模型”容易冲突。建议直接删除。若产品坚持保留，必须补充负余额、赠送优先、当前单价变化和不可作为合同承诺等规则，且只能由 Core 计算返回，前端不得用余额除以单价。

## 4. 技术设计需要调整的内容

### T1. 更新 Web 页面结构和路由

技术 §13.1 建议改为以下目标路由：

| 路由 | 页面 | 可恢复状态 |
|---|---|---|
| `/` | 工作台 | 当前任务、概览视图 |
| `/students` | 学生与账户 | 搜索条件、状态筛选、学生 ID、页签、课程账户 ID |
| `/schedule` | 排课与课消 | 周起始日、老师、课程、状态、选中课程 ID |
| `/finance` | 收支与报表 | 月份、页签、老师/分类筛选 |
| `/tasks/:threadId` | 最近任务恢复 | 消息、Run、Workspace、Preview、Receipt |

具体是否使用 path 或 query parameter 可以实现时决定，但刷新、深链和权限变化后的行为必须可测试。不能只把关键状态保存在组件内存。

### T2. 增加公开结构化读模型 API

现有技术设计较完整地定义了 Agent 内部 Tool API，但没有为新原型的常驻页面定义公开聚合读模型。建议在 §12 增加浏览器使用的 Core Public Read API，并通过 OpenAPI 生成 Client。建议至少包含：

- 工作台概览：同一响应返回指标、待办、最近业务记录和数据时间点；
- 学生目录与学生详情：服务端搜索、权限过滤、分页、计算学籍；
- 学生课程账户与流水：Core 返回实收、赠送、总余额、当前单价和来源记录；
- 周课表：按业务时区返回完整日期范围和课程状态；
- 月度财务概览：经营、现金双口径及关键差异项；
- 工资列表/详情；
- 关账前检查：阻断、提醒、检查时间和来源记录。

公开读模型与 Agent Tool 可以复用同一 Application Service，但应使用不同 Controller、鉴权和 DTO；前端不得并发拼装后再自行计算经营指标。

### T3. 扩展 `WorkspaceDocument` 白名单和版本策略

技术 §12.5 现有白名单无法完整表达账户详情、工资和关账检查。建议：

- 增加 `student-detail`、`course-account-detail`、`weekly-schedule`、`finance-comparison`、`payroll-detail`、`preclose-checklist`、`task-history`；
- 每个组件有独立 `schemaVersion`；未知版本只读降级；
- 组件只包含结构化数据、来源 ID 和允许动作，不包含 HTML、脚本或前端计算表达式；
- 普通路由页面可以直接使用 OpenAPI DTO；只有需要随对话流式替换的区域进入 `WorkspaceDocument`，避免把整个页面都变成服务端驱动 UI。

### T4. 定义“结构化按钮 → Preview”的统一链路

新原型的按钮不能在生产实现中只向聊天框注入文字。技术 §8、§13 应补充：

```text
结构化按钮
  → 打开本地类型化表单或选择器
  → 浏览器请求 Core Preview API
  → 本地 actionType + schemaVersion 组件渲染预览
  → 浏览器携带用户 JWT 直接确认
  → 查询并展示 Core Receipt
  → 如存在当前任务，再把 Preview/Receipt 摘要同步到该任务
```

该链路不经过模型，也不允许 Agent 代为确认，继续遵守 R14。

### T5. 明确任务状态、页面状态和领域事实的边界

在技术 §13.2 的三类状态基础上增加：

- `activeThreadId` 是全局任务状态，不按四个页面复制聊天数组；
- 路由筛选和选中项属于可恢复 UI 状态；
- 当前余额、课程状态、工资和报表属于领域事实，切页、恢复和确认前均从 Core 重新读取；
- 导航触发的上下文建议必须显式传递，不从页面文本或旧聊天推断；
- Preview 和 Receipt 以 Core 记录为准，聊天仅持有引用。

### T6. 角色化导航和服务端授权

技术 §14.1 建议补充两层控制：

1. 前端根据 `/auth/me` 返回的能力集合渲染导航、按钮和路由；
2. Core Controller/Service 仍执行 `JwtAuthGuard + RolesGuard + 资源级授权`，不能依赖导航隐藏。

老师访问店主路由时应返回统一的无权限页面，不能先加载敏感数据后再隐藏。历史任务和深链每次打开都重新校验当前角色与教师归属。

### T7. 增加读模型一致性和刷新策略

工作台概览、详情和列表之间需要明确一致性策略：

- 所有金额继续使用两位小数字符串，前端不使用 `number` 运算；
- 概览响应携带 `asOf`/业务时间和来源范围；
- 写操作成功后按 Receipt 中的失效标签刷新相关 Query；
- SSE 的 `workspace.patch` 只更新展示，不替代 Core 事实查询；
- 切换学生、月份、周次或角色时取消旧请求，避免旧响应覆盖新页面；
- 长列表服务端分页和筛选，不向模型或浏览器一次返回全量敏感记录。

### T8. 增加新原型对应的 E2E 与视觉验收

技术 §17 建议增加：

- 四个一级路由的桌面、平板、手机布局；
- 路由刷新、深链、返回、会话恢复和 Preview 恢复；
- 店主/老师导航和数据隔离；
- AI 不可用时，四页的关键查询和 L1/L2 操作仍可完成；
- 结构化按钮与 AI 指令生成相同 Preview/Receipt；
- 工作台指标点击后与明细数量、金额和状态一致；
- 完整七天课表、跨月周、空状态、长姓名、长金额、负余额；
- 键盘操作、焦点顺序、状态非纯颜色表达；
- 未知 Workspace/Preview schemaVersion 的只读降级。

## 5. 原型需要修改，但不应反向修改需求的内容

| 原型问题 | 原因 | 建议 |
|---|---|---|
| 工作台显示“今日 6 节”，今日排课明细只显示 2 节 | 同一事实不一致 | 使用一套示例数据源，或明确指标/列表的过滤差异。 |
| “陈一：冻结 · 31天未上课” | 冻结规则是“超过 31 天”，第 31 天仍在读 | 改为“超过31天”或“32天未上课”。 |
| 选择陈一后仍显示“在读”和林悦的手机号/账户 | 示例状态未联动 | 每个学生使用独立资料和账户；冻结学生仍可有账户，但状态必须一致。 |
| 周视图只有周一至周五 | 需求没有排除周末课程 | 默认展示完整 7 天，或让隐藏周末成为明确可切换偏好。 |
| 新建学生、交费、调课等都返回同一“补充金额、时间或渠道” | 不同动作必填字段不同 | 使用 actionType 对应的字段 Schema 和最少补问。 |
| L1/L2 只有说明卡，没有可核对 Preview、最终按钮、失效和回执 | 不满足冻结确认协议 | 补齐预览、返回修改、明确确认、执行中、失效、成功/失败回执状态。 |
| 没有同名学生/多课程候选卡 | 不满足核心验收 | 增加实体候选选择状态，选定前不展示敏感金额。 |
| 没有批量排课、冲突日期和整批失败状态 | 不满足 MVP 必做 | 在排课页增加批量入口和完整预览。 |
| 没有最终退款、课消撤销、资金冲正、取消工资支付和重开账入口 | 结构化降级不完整 | 放入对应详情/更多操作，但不能仅依赖 AI。 |
| 关账把未支付工资直接定义为唯一阻断，并展示 75% | 阻断等级尚未冻结 | 先完成 D6，再由 Core 返回 blocker/reminder/percentage。 |
| 页面右上角“通知”按钮无定义 | 本期不做站外通知，站内通知中心也未定义 | 若只是装饰则删除；若保留，先补需求范围和数据来源。 |
| 原型依赖本地正则生成业务回复和金额 | 只能用于演示 | 生产实现只使用真实 Core 查询、Preview 和 Receipt；原型文案不得作为验收证据。 |

## 6. 建议的文档落地顺序

1. 先评审并确认 D1–D7；
2. 新建《系统需求设计 AI Native（MVP v1.1 评审稿）》，不直接覆盖已冻结 v1.0；
3. 仅在 D5、D6 通过时，新建《系统需求设计 V2（MVP v1.1 评审稿）》补业务字段和关账阻断规则；
4. 新建《系统技术设计 AI Native（MVP v1.1 评审稿）》，同步更新页面、API、协议和测试；
5. 更新原型，至少补一条 L1、两条 L2、同名消歧、任务恢复、老师视图和移动端关键流程；
6. 文档与原型评审通过后再分解实现任务，不能用原型示例数据代替业务验收。

## 7. 本次不建议改变的基线

以下内容不因新原型而调整：

- 学生与课程唯一确定一个金额账户；
- 实收和赠送分池，赠送优先扣除；
- 金额、工资、退款、关账和报表只由 Core 计算；
- L1/L2 必须先 Preview，用户确认后才能执行；
- Agent 只读和申请 Preview，不能调用 Confirm/Execute；
- 浏览器用用户登录态直接向 Core 确认；
- 老师不能查看学生余额、交费、退款、其他老师工资和全店经营报表；
- 月度现金口径与经营口径继续分离；
- 不引入剩余课次、课包、第二模型供应商、多 Agent、Redis 或向量数据库；
- AI 不可用时，结构化关键业务仍可用。
