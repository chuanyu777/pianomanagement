# AI对话架构调整建议

> 依据：本轮AI专项实测。状态：调整建议，尚未实施，不替代冻结需求。

## 1. 是否需要调整设计

需要系统性调整**对话实现**，不需要推倒Core领域模型或扩充产品范围。

重新核对冻结技术设计后，发现其中已经规定了模型理解、任务上下文、候选选择、interrupt补参、受权查询及逐项预览确认。当前代码只实现了局部固定命令和摘要回答，未完整落地这些职责。因此优先纠正实现偏差，并补充状态生命周期、权限投影和验收约束，不能把问题归成模型能力不足。

保留现有React、NestJS、Fastify、LangGraph、两个PostgreSQL及单一DeepSeek供应商；继续单Agent实例。两人使用的MVP不引入DeepAgents、Redis、向量库、生产多Agent或开放式自动规划。

## 2. 为什么现有方式无法靠补句式解决

| 当前实现及位置 | 造成的问题 | 调整方向 |
|---|---|---|
| business-query-graph.ts的parseBusinessIntent/parseReadScope | 固定关键词/正则决定业务，昨天、明天、语序和标点持续遗漏 | 模型输出受校验的结构化意图；正则仅做格式校验或显式快捷入口，不当唯一业务理解入口 |
| 同文件answerQuery | 模型仅润色dashboard，无法选择其他必需工具 | 模型参与意图和槽位提议，编排层校验，Core负责事实和业务规则 |
| App.tsx submit每次createAssistantIds | 页面没有持续的同一业务任务 | 新建任务才生成thread，每轮消息生成独立run |
| run-executor.ts以threadId:runId作checkpoint | 后端即使同thread也不保留业务上下文 | 持续任务状态与单轮运行/事件分别管理，按thread串行更新任务版本 |
| resume只接approved，server恢复Spike Graph | 无法恢复对象选择、补字段或取消 | 有类型的补充字段/选择/修改/取消输入，接回真实业务Graph |
| Web只消费部分WorkspaceBlock | 协议已有候选等块，但页面无法完成选择 | 按共享传输协议完整解析和渲染本期块及sources |
| Core上课预览统一L1且无角色投影 | 风险降级、教师看到学生资金 | Core权威动作元数据及角色专属公开投影，Agent不能自行推断风险 |

这些位置仅用于定位当前偏差，不从代码反向定义需求。领域DTO和角色仍使用Core OpenAPI生成Client，不另抄实体/枚举。

## 3. 调整后的职责分工

1. 模型：理解“查什么/办什么”、提出时间和字段、识别更正及取消、根据真实工具结果解释。不能计算余额、决定权限或生成成功凭证。
2. 编排：加载当前任务，校验意图和字段，定位真实对象ID，补问/选择，执行有限步骤，申请Preview并维护每步状态。
3. Core：鉴权和数据范围、确定性业务规则、资金计算、动作风险级别、版本校验、幂等预览、最终确认和回执。
4. Web：显示持续对话与相关工作区，提交选择/补充信息；最终确认直接携带当前登录态调用Core，不经Agent代办。

模型输出必须经过schema校验及工具白名单。未理解、无权限、缺字段分别处理；禁止解析失败后擅自回落到收入、排课或其他写操作。

## 4. 连续对话和任务状态

### 4.1 同一任务与新任务

- thread是持续任务；run是一轮输入的处理记录，不混作同一个标识。
- 同一任务保存明确的业务意图、已确认对象ID、字段来源、待补字段、候选集合、步骤状态、当前预览和引用来源。
- 新建任务不继承旧任务金额、渠道、退款对象、工资月份等敏感参数。
- 上下文按权限裁剪，模型不持有无限历史；不做长期偏好记忆。

### 4.2 补充、更正与取消

- “支付宝”只填当前待补渠道；不存在该待补任务时先询问用途。
- “选择第二个”必须绑定当前候选列表及版本，并回传真实对象ID；不能全局搜索第二个人。
- “不是1000，是100”更新明确字段，重新申请Core预览。旧预览需按既定取消/替代状态失效，不能只从页面移除。
- “先别收，只查余额”结束待办理动作，撤销其可确认性并转入只读查询；已提交的动作先核对Core结果，不伪称已撤回。
- 每轮重新识别后显式清除不再适用的intent/字段。**只把checkpoint键改成threadId会留下旧intent，已由离线测试发现风险。**

状态、更新方式、任务版本与幂等输入应在实施前写成类型和测试。保持现有租约fencing，不以保留上下文为由绕过运行并发保护。

## 5. 查询和业务工具

先按冻结需求人工列必需能力，再独立检查实际注册工具及Core内部API，不能由工具注册表生成需求清单再声称覆盖完整。

- 课表查询使用日期范围、老师/学生/课程/状态参数，不依赖今日dashboard。
- 支持受权基础资料、课程账户、流水、欠费/冻结名单、课消、工资及月报明细查询。
- 基础资料维护、开户改价和其他本期操作必须有对应Core Preview及Confirm闭环；不能直接把公开写API注册给Agent。
- 一句话多个动作仅形成有限有序步骤，分别确认；上一项回执成立后才生成依赖它的下一项预览。不做自主补偿、自动退款或任意混合批量执行。

时间在受控Asia/Shanghai业务日历中解析和验证，写入UTC；无法唯一确定的“最近几天”等补问。模型提出日期不能替代非法日期、时区、课程时长及冲突校验。

## 6. 权限与风险的优先修正

教师资金泄露必须在Core出站边界修复：教学确认视图与店主资金视图分开。不能仅在React隐藏字段，也不能先把完整资金display发给模型再要求其别说。

对历史预览、回执、来源链接和重新连接的事件重新检查当前角色及数据范围；既有预览可能已保存敏感display，修正时需要处理历史响应投影，但不删除审计历史。教师可见教学资料/本人业绩工资按冻结规则返回。

Core按动作确定风险级别：上课确认和撤销确认属于L2；排课、调课、取消属于L1。API返回权威风险元数据，Web和Agent使用同一结果，不再用`lesson.*`推断。已有预览的风险值需有明确兼容/失效方案，不能静默保留错误等级。

## 7. 工作区与错误处理

- 工作区仅显示当前问题相关结果、必要筛选、候选、预览或回执；不恢复常驻施工说明。
- 采用共享Workspace协议，补齐本期选择卡、日历/课表、流水明细、来源链接和恢复操作；不另手写缩减版协议后丢弃合法块。
- 记录候选或预览所属任务及版本，禁止旧卡影响新任务。
- Core的403权限、409状态/版本/冲突、参数错误、空结果、网络超时及500分别映射稳定公共错误。500依旧通用文案，细节只进脱敏日志。
- 保留可安全重试的已明确参数，但先按原请求ID查结果；不得因为断网新建另一笔资金请求。

## 8. 建议实施顺序

1. 先修教师响应投影与Core风险级别，增加真实响应的负向断言，禁止敏感字段仅靠前端隐藏。
2. 落实thread/run分离、业务任务状态、有类型的补问恢复、更正/取消及旧预览失效；与模型理解节点一起打通。
3. 先完成一个可验收闭环：“昨天/明天/范围课表 → 那明天呢 → 只看某老师 → 选择一节 → 调课预览 → 浏览器确认 → 回执”。
4. 打通资金闭环：“找学生/同名选择 → 分课程余额 → 交费缺渠道 → 补支付宝 → 改金额 → 取消/严格确认 → 原记录”。
5. 按独立需求清单补齐基础资料、赠送/冲正、批排、退款、工资、收支、关账及有限多步骤，不把前两个闭环当成全部完成。
6. 恢复固定时钟和各组数据，执行83条全部适用步骤、变体及A01–A08；再执行真实模型重复样本、异常恢复、教师权限及多设备检查。

每阶段先使用本轮已见红检查，再增加与真实HTTP/Web一致的测试。离线预期工具命名不作为新接口既成规范，最终绑定经评审的生成Client；金额结果最终必须与真实Core和原始记录核对。

## 9. 本轮没有实施的内容

本轮仅测试、定位和提出调整建议，没有重写Graph、修改Core权限或更改前端交互。上述修正实施后仍需按仓库规约运行完整门禁及相关集成/E2E；本轮“只测AI”的结果不能替代实施后的完成门槛。
