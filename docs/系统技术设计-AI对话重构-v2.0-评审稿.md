# 系统技术设计：AI 助手对话链路重构（v2.0 评审稿）

日期：2026-10-28
状态：待评审，未实施
影响范围：`apps/agent-runtime`（主）、`apps/core-api`（补校验）、`apps/web`（错误展示）

## 1. 为什么重构

现有实现在"能跑通"这一层是达标的，但结构上有三个互相纠缠的问题。

**职责三重混淆。** 意图层同时承担意图分类、参数抽取和业务规则拒绝。`deterministicIntent` 里有近百条中文正则，既判断"交费100"是交费，又抽金额和渠道，还负责拦"工资先发500""退款手续费登记成收入""跨课程抵扣欠费"。三种职责混在一起，导致每加一条业务规则都要动意图匹配，且规则之间会互相干扰。

**双通道行为不一致。** 命中正则走确定性路径，没命中才调模型。两句人类看来相似的话可能走完全不同的代码分支，输出风格和质量都不同。更严重的是意图解释器整体依赖模型，模型不可用时连规则能识别的请求也一起失效，`dialogue-graph.ts` 第 255 行直接返回「AI暂不可用」。

**工作流是包装而非编排。** `createDialogueGraph` 只有三个节点，`loadContextAndWithdrawPreview → understand → resolveAndReadOrPreview`，三条边全部是线性的，「提前结束」是唯一分支。没有循环、没有 `interrupt`、`compile()` 连 checkpointer 都没传。多轮确认靠 `dialogue_tasks.state` 加新 run 实现，不靠图的断点恢复。而真正的业务逻辑全部堆在 `resolveAndReadOrPreview` 这一个节点里，代码超过一千行。

结论：需要把「理解」「规则」「编排」「渲染」四件事拆开，而不是在现有结构上继续加正则。

## 2. 设计原则

| 原则 | 含义 |
|---|---|
| 模型只负责理解 | 模型把自然语言映射成结构化意图，不计算、不判断业务规则、不复述金额 |
| Core 是唯一规则源 | 所有业务校验、拒绝理由、金额计算都在 Core，Agent 不再预判 |
| 编排是纯函数 | 一次 run 是 `(task, message) → (task', result)` 的确定性转换，可单测 |
| 回答数字模板化 | 面向用户的业务数字一律模板渲染，模型只生成澄清提问和引导话术 |
| 失败必须可解释 | 理解失败要退化成澄清，不能变成 run failed |

## 3. 新分层

```
浏览器 ──JWT──> Core Gateway ──Capability──> Agent Runtime
                                              │
                                    ┌─────────┴──────────┐
                                    │ 1 Understand       │ 模型：消息 → 结构化意图
                                    │ 2 Plan             │ 纯函数：意图 + 任务 → 下一步
                                    │ 3 Act              │ 调 Core 只读 / 申请预览 / 要求澄清
                                    │ 4 Render           │ 模板：结果 → 回答与工作区
                                    └────────────────────┘
                                              │
                                        Core（唯一规则源）
                              领域服务校验 · 金额计算 · 预览 · 确认后落库
```

四步之间不共享可变状态，每一步的输入输出都是可序列化的数据。这意味着每一步都能单独写单元测试，不需要起图、不需要 mock 整个 Core。

## 4. 意图层：去掉正则

### 4.1 输入与输出

输入包含四部分：用户原话、当前任务摘要（operation、已收集字段、状态、候选）、业务日期与星期。业务日期必须显式传入，否则模型无法把「下周三」换算成具体日期。

输出仍是严格 JSON：`mode`（new/continue/correct/cancel/clarify）、`operation`（36 个能力之一或 null）、`fields`（受 operation 字段白名单约束）、`question`（澄清用语）。

### 4.2 校验与重试

第一层用 zod 校验结构和字段白名单，模型输出多余字段直接判失败。失败后重试一次，第二次仍失败则执行降级，而不是抛 `AI_INTENT_INVALID`。

### 4.3 失败降级（关键改动）

| 情况 | 现状 | 新设计 |
|---|---|---|
| 模型输出非法 JSON，两次重试 | 抛错，run 失败，用户看到「AI处理暂时失败」 | 退回手工澄清：「我没听清，你是想办理交费、排课还是查询？」并给出三个可点击建议 |
| 模型不可用（无 key、超时、欠费） | 整个对话返回「AI暂不可用」，规则也不跑 | 返回明确的降级提示，并提示可使用结构化页面，run 状态为 completed 而非 failed |
| 模型给出了 operation 但缺参数 | 已有询问逻辑 | 保留，这是现有实现最好的部分 |

### 4.4 正则的替代物

去掉正则不等于放弃对高频说法的控制，但手段换成提示词里的示例，而不是代码里的分支：

- 每个 operation 给两到三个典型说法作为 few-shot 示例，写在系统提示词里。
- 相对时间（今天、明天、下周三、这个月）由模型结合传入的业务日期换算，Agent 只做格式校验。
- 金额、比例、时长等精确值由模型原样提取，Core 用已有正则做格式校验（Core 侧本来就有金额格式校验，属于领域约束，应当保留）。

## 5. 被删除的规则与替代方案

我逐条核对了现有正则拦截，实际安全性由 Core 兜底，正则大多只是"提前给一句好听的话"。

| 原有正则拦截 | Core 实际行为 | 处理 |
|---|---|---|
| 工资分批支付 | `payroll.pay` 只接收渠道、时间、备注，**没有金额参数**，天然只能整笔支付 | 删除。预览会显示整笔实发金额，用户确认时即可看到；无需 Agent 预判 |
| 已关账工资不可调整 | `payroll.payInTransaction` 调用 `periods.assertWritableForDate` | 删除。把 Core 的 409 文案翻译成人话即可 |
| 跨课程抵扣欠费 | 退款按账户分账处理，无法跨账户抵扣 | 删除 |
| 退款手续费重复登记为收入 | 手工收支有固定分类枚举，无"退款手续费"类目 | 删除正则，改为澄清："手续费会随退款自动入账，不需要单独登记，你是想登记其他收入吗？" |
| 无法识别的请求 | 返回「请说明希望先查询或办理哪一项业务」 | 改为带建议的澄清，复用同一套话术 |

配套要求：Core 需要补两处显式校验，否则删除正则后会出现"能提交但结果不符合业务预期"的情况。一是手工收支的兜底分类不得用于退款手续费语义，二是在 409/403 返回中带上机器可读的 `reason` 字段，供 Agent 翻译成中文引导。

## 6. LangGraph 的去留

### 6.1 结论

**建议在对话链路移除 LangGraph，改为显式状态机。** `business-query-graph` 一并移除，其职责并入新的 Plan/Act 两步。

### 6.2 判断依据

| 检查项 | 事实 | 结论 |
|---|---|---|
| 节点数与拓扑 | 3 个节点，3 条线性边，唯一分支是提前结束 | 没有编排需求 |
| 循环与重试 | 无 | 无 |
| `interrupt` / `Command(resume)` | 对话链路完全未使用 | 多轮确认不依赖图 |
| checkpointer | `dialogue-graph` 的 `compile()` 无参，未启用 | 持久化实际由 `dialogue_tasks` 承担 |
| 持久化方式 | 自定义 PostgreSQL 表 `dialogue_tasks` | 与 LangGraph 无关 |
| 业务逻辑分布 | 1000 余行集中在单个节点内 | 图并未带来模块化 |

换句话说，LangGraph 在这里只做了「把三个 async 函数串起来」，而这件事用一个 30 行的 pipeline 就能完成，且更容易测试和阅读。

### 6.3 替代方案

用显式状态机表达会话生命周期：

```
idle ──用户消息──> collecting ──参数齐全──> ready ──生成预览──> awaiting_confirmation
                        │                                          │
                        └──缺参数──> 询问（回到 collecting）        ├──用户确认──> executed
                                                                   └──用户放弃──> cancelled
```

每次 run 执行一次转换：读取 task → 调模型理解 → Plan 决定动作 → Act 调 Core → Render 输出 → 写回 task。状态迁移由纯函数决定，非法迁移直接抛错。这套结构用现有 `dialogue_tasks` 表就能承载，不需要新增存储。

### 6.4 如果坚持保留 LangGraph

那就必须让它承担真正需要图能力的事：把「确认」做成 `interrupt`，把一千行的 `resolveAndReadOrPreview` 拆成 `resolveObjects`、`collectFields`、`buildPreview`、`renderResult` 等节点。否则保留它只是增加阅读成本。这一点需要在评审时明确取舍。

### 6.5 迁移风险

行为等价，现有 381 条 Agent 测试与 108 条 Web 测试可作为回归基线。风险主要在于测试文件大量直接构造 `createDialogueGraph`，需要同步改造为构造 pipeline。建议保留一个兼容层，先用新 pipeline 实现、旧图转调新实现，跑一轮全量测试后再删除旧图。

## 7. 回答渲染

取消 `answerQuery` 里让模型润色经营摘要的做法。理由是收益低、风险高：摘要本身已经是结构化的中文短语，模型润色带来的自然度提升有限，却引入了「已完成」被误判成"声称已执行"这类误伤，以及编造数字的风险。

新规则：

| 内容类型 | 生成方式 |
|---|---|
| 业务数字、余额、报表、工资明细 | 模板，字段与顺序固定 |
| 澄清提问、缺参数追问 | 模板 + 可选模型改写（仅改语气，不改事实） |
| 错误引导、权限说明 | 模板，按 Core 返回的 `reason` 映射 |
| 能力介绍 | 模板 |

模型在整条链路中只出现一次，就是 Understand 那一步。

## 8. 数据模型变更

`dialogue_tasks.state` 增加 `schemaVersion` 字段，便于后续演进时兼容旧任务。删除 `fields.reason` 中用于承载正则判断结果的魔法字符串（如 `'工资不支持分批支付'`、`'已关账工资不可调整'`），这类信息改由 Core 的 `reason` 表达。

新增可选表 `intent_audit`：记录每次理解的原话、模型输出、最终 operation、是否发生重试。用于评估准确率和回归对比，默认关闭写入。

## 9. 分阶段实施

| 阶段 | 内容 | 验收 | 可回滚点 |
|---|---|---|---|
| 一 | 意图层单一入口：模型为主，规则仅影子对照（只记日志不生效）；补失败降级 | 固定 60 条语料意图准确率 ≥95%；模型不可用时不出现 run failed | 规则仍可一键恢复 |
| 二 | Core 补两处校验与 `reason` 字段；删除全部业务拦截正则 | 删除的每条规则都有对应测试，且测试落在 Core 或模型契约层 | 保留旧正则文件不删 |
| 三 | 拆 `resolveAndReadOrPreview` 为 pipeline 四步；移除 LangGraph 依赖 | 全量测试通过，行为逐条比对一致 | 保留兼容层 |

每阶段独立可上线，前两阶段不改变工作流结构，风险最低。

## 10. 验收标准

意图准确率以现有测试语料加真实对话采样构建 60 条固定集为准，覆盖 36 项能力与常见否定、纠正、切换场景，准确率不低于 95%，且任何情况下不得把 A 业务识别成 B 业务后直接生成预览。

降级可用性：模型不可用时，用户仍能看到「助手暂不可用」的明确提示和结构化入口，不出现空白、不出现英文报错、不出现任务卡在 running。

性能：单轮首字延迟 P95 不超过 3 秒；纯查询场景不超过 2 秒。

可测性：pipeline 四步的每一步都有输入输出契约测试，不依赖真实模型和真实数据库。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型对精确参数抽取不稳 | 日期、金额理解偏差 | 强制回填确认，预览页展示解析结果；金额格式由 Core 二次校验 |
| 延迟与成本上升 | 每次对话至少一次模型调用 | 本地与两人使用场景可接受；后续可加高频说法缓存 |
| 去正则后出现"能提交但不符合业务预期" | 数据正确性 | 阶段二必须先补 Core 校验再删正则，顺序不可颠倒 |
| 移除 LangGraph 改动面大 | 回归风险 | 分阶段 + 兼容层 + 现有测试基线 |

## 12. 会话上下文与生命周期

原稿遗漏了这一块，而它决定了长对话是否可用，必须明确。

### 12.1 三层上下文，各管一件事

| 层 | 承载什么 | 谁在用 | 生命周期 |
|---|---|---|---|
| 会话 thread | 话题边界、标题、消息列表 | 界面展示、审计、追溯 | 用户或规则决定何时新建 |
| 任务 task | 当前正在办的一件事：操作类型、已收集参数、已选对象、预览、进度 | 编排与理解 | 换话题即重置，任务结束置为 completed/cancelled |
| 消息 message | 逐条原话与回复 | 只做展示与审计 | 随会话增长 |

关键取舍：**任务状态参与决策，消息历史不参与**。模型输入固定为业务日期、任务摘要、当前消息三项，不追加历史消息。

这么做的好处是输入大小恒定，长对话不会越来越慢、越来越贵，也不会被前面的错误内容带偏。代价是指代只能依赖任务里的字段继承，无法回答"上周那个价格是多少"这类需要回看历史的问题。这是有意接受的能力边界，不是缺陷。

### 12.2 长对话会遇到的具体问题

| 问题 | 表现 | 现有机制的应对 | 是否够 |
|---|---|---|---|
| 跨任务指代失效 | 用户说"就刚才那个"，任务已重置，无法解析 | 无 | 不够，需要澄清追问并给出候选 |
| 中途切换导致进度丢失 | 办到一半去问别的，回来参数已清空 | 换话题即重置任务 | 可接受，但应提示"刚才那笔已中断" |
| 完成任务后继续说 | 携带 `alreadyExecuted`，可能误把"再交一次"理解成重复提交 | 模型可见该标记 | 基本够，预览仍可拦截 |
| 多任务无法并行 | "先给小明交费，再给小红排课"只能走预先写死的两步方案 | 多步计划仅支持特定组合 | 不够，MVP 阶段明确不支持任意并行 |
| 会话过长标题失真 | 标题取首条消息，之后办了十几件事仍显示第一件 | 无 | 需要按任务刷新标题 |
| 消息表无限增长 | `agent_messages` 只增不减 | 无清理 | 需要保留期策略 |
| 悬空预览 | 旧任务有未确认的预览，用户换话题，预览仍在有效期 | 换话题时撤销旧预览 | 够 |

### 12.3 该什么时候新建会话

按必要性分三档，可作为产品规则也可作为自动提示。

| 档位 | 场景 | 处理 |
|---|---|---|
| 必须新建 | 跨业务日期（今天/明天这类相对说法会漂移） | 自动新建并提示 |
| 必须新建 | 上一任务已有待确认预览，用户要办另一件事 | 先让用户放弃或确认旧预览，再新建 |
| 建议新建 | 上一任务已 completed 或 cancelled，新消息属于不同操作 | 提示"这笔已办完，是否开始新任务" |
| 建议新建 | 单会话已完成三个以上互不相关的任务 | 提示收敛话题 |
| 建议新建 | 距上一条消息超过八小时 | 新消息时自动新建，保留历史可查 |
| 不必新建 | 同一任务补参数、改参数、纠正、切换候选 | 继续用当前任务 |
| 不必新建 | 同一学生的连续操作，如再交一笔 | 继续用当前任务，保留对象 |

不建议做成"强制一刀切"。用户在同一会话里连续办同一学生的几件事是完全合理的，强行切开会丢失已选对象，体验更差。关键是**任务边界必须清晰**，而不是会话边界必须短。

### 12.4 实现要点

任务重置时，除操作类型与最近一句原话外全部清空，这与当前实现一致，保留。新增三项能力：

一是任务结束时写入 `endedAt` 与结束原因，供"是否建议新会话"的规则读取。

二是会话标题在每次任务完成时按最新任务刷新，避免标题长期停留在第一件事。

三是新增会话保留期配置，消息默认保留九十天，超出部分归档或清理，避免 `agent_messages` 无限膨胀。

## 13. 补充约束（第二轮回审补漏）

以下七项在第一版设计稿中缺失，其中前两项属于上线前必须解决。

### 13.1 隐私：用户原话与任务字段会原样发给第三方模型

现状是 `new HumanMessage(JSON.stringify(context))`，其中 context 包含 `userMessage`、`task.fields`、`task.candidates`、`task.references`。也就是说，「给小明交1000」这句话以及候选人列表里的学生姓名、以及金额，都会完整进入 DeepSeek 的请求体。这不是新设计引入的问题，但新设计把模型用于每一次理解，等于把原本偶尔发生的数据外传变成每次对话都发生。

必须在设计里明确边界，三选一：接受并写入数据条款；对姓名做代号替换后再发送；或改用支持私有化部署的模型。MVP 阶段建议采用第二条的轻量做法：发送前把学生与教师姓名替换为「学员A」「教师B」，模型只负责理解结构，姓名与 ID 的绑定在本地完成。实现成本低，且不影响意图识别准确率，因为模型只需要知道「这是一个学生实体」。

同时明确禁止向模型发送电话、备注、流水明细等无关字段。

### 13.2 并发：同一会话没有互斥保护

`startRun` 每次生成新的 `runId`，没有检查该会话是否已有正在执行的运行。用户在界面上连点两次发送、或在两个标签页同时操作同一会话，会产生两个 run 并发读写同一份任务状态。后者会互相覆盖字段，最坏情况是生成两张预览、用户各确认一次。

必须补：会话级互斥，同一 `threadId` 同时只允许一个 `running` 运行，第二个请求返回「上一条还在处理中」；前端在等待期间禁用发送按钮。

### 13.3 取消语义未定义

状态机里有 `cancelled`，但没有定义「取消什么」。用户说「算了」时，需要明确取消的是当前任务、待确认预览、还是整个会话。多步任务进行到第二步时取消，第一步已经确认入账的部分如何表述，也没有规定。

建议明确：取消仅作用于当前任务；已确认的步骤不回滚，回复中必须逐条说明哪一步已生效、哪一步未执行。

### 13.4 多步任务缺少事务边界

现有实现支持「交费+赠送」「工资撤销+重新支付」等固定两步组合。第一步确认成功、第二步放弃时，业务上处于中间状态。设计稿只写了「保留多步能力」，没有定义补偿或提示策略。

建议：每一步独立事务，不追求跨步原子性；任务状态记录每一步的预览与回执，第二步未执行时，回答里必须写明「第一步已生效，第二步未执行」，并提供继续第二步的入口。

### 13.5 去掉正则后失去确定性兜底，但没有可观测性

这是本次重构最大的隐性风险。现状是「正则命中就不调模型」，等于有一层稳定兜底；去掉后，所有理解都依赖模型，模型质量波动会直接变成用户体验波动。设计稿只说了「失败降级为澄清」，没有说如何知道降级是否频繁。

必须补指标，至少四项：识别成功率、澄清率（模型主动追问的比例）、重试率（首次输出不合法）、平均完成轮次。指标落到 `intent_audit` 表，按天聚合。当澄清率超过阈值时，应能定位到具体是哪类说法识别不好，而不是整体回退到正则。

### 13.6 提示词成为核心资产，但缺少版本与回归机制

去掉正则后，36 项能力的识别语义全部承载在系统提示词里。改动一句措辞可能同时影响多个能力，而现在没有任何版本号，也没有基线语料。

建议：提示词独立成文件并带版本号，与代码同仓管理；建立不少于 60 条的基线语料，每条包含原话与期望的 operation；每次修改提示词必须跑基线并记录准确率，低于阈值不允许合并。这条与第 10 节的验收标准配套。

### 13.7 金额与日期的歧义没有处理规则

「一千」「1千」「1000块」「下周三」「月底」「这周」这类表达，设计稿笼统地写「交给模型」，但没有规定歧义时应当追问还是直接取值。

建议：金额必须归一为两位小数并在预览中回显；相对日期必须回显绝对日期，例如「明天（10月29日）」。凡是回显与实际理解不一致的场景，用户能立刻发现，这是成本最低的纠错手段。

### 13.8 次要但需登记的两项

审计目前靠 `BusinessAuditEvent.runId` 是否存在来推断是否由 AI 参与，建议在 `detailJson` 中显式写入 `origin: 'AI_PREVIEW' | 'MANUAL'`，便于后续核对「哪些操作是 AI 促成的」。

模型超时目前是干等十五秒后降级。建议在等待超过两秒时先推送一条「正在理解」的进度事件，避免用户以为卡死。

## 14. 用户侧场景（第三轮回审）

前两轮从系统内部审，这一轮只问一个问题：用户实际会遇到什么。以下四项已验证，其余为代码审读结论。

### 14.1 重复提交没有幂等（已验证）

实测同一 `clientRequestId` 连续提交两次，服务端返回两个不同的 `runId`，两次都正常执行。原因有两处：网关的 `startRun` 每次都生成新运行，未按幂等键去重；前端 `createAssistantIds()` 每次发送都重新生成 `clientRequestId`，重试时不可能复用同一个键。

后果是网络抖动、用户手快连点、或前端重试时，同一句话会被处理两遍。查询类只是多花一次 token，写入类会生成两张预览，用户各确认一次就重复入账。

处理：服务端按 `clientRequestId` 做去重，重复请求直接返回首次的运行标识；前端在重试路径复用同一键，只有用户主动修改内容时才换新键。

### 14.2 输入校验的错误提示不可读（已验证）

超过四千字返回「请求参数不合法」，纯空格和空字符串同样返回这七个字。用户不知道是太长、太短还是格式不对。

处理：按失败原因返回具体提示。「消息过长，最多 4000 字」这类文案应当由服务端返回，前端不能自己拼。

### 14.3 空数据时的首次体验缺失

新开店的库里没有任何学生、课程、排课。此时提问得到的回答是「今日排课 0 节」「共 0 条工资记录」。形式上正确，但用户无法区分「确实没数据」和「功能坏了」。

处理：识别到关键实体数量为零时，改为引导式回答，例如「还没有学生和课程，先建一门课程再排课会更快」，并给出跳转入口。这属于答案模板的分支，不需要额外机制。

### 14.4 权限不足是碰壁式发现

老师账号能问什么、不能问什么，界面上没有任何说明。老师问经营收入才被告知无权限，问退费才提示无权操作。用户要靠试错建立心智模型。

处理：按角色提供不同的示例问题，老师首页只展示他能做的事（课表、课时、工资）；同时在能力清单里明确标注角色限制，模型在接到越权意图时直接给出替代路径。

### 14.5 断线与恢复

后台标签页放置较久、锁屏、地铁里断网，都会导致长连接中断。当前实现有 `Last-Event-ID` 补读，重连后能补齐事件，这部分是够的。不足在于没有自动重连，用户需要手动再发一条消息。

处理：识别到流异常中断且运行未终结时，自动重连一次并提示「连接中断，正在恢复」；两次失败再交给用户。

### 14.6 说错话没有纠错入口

用户说「给小明交2000」，发现说错了，只能再补一句「改成1000」。没有撤回、没有编辑。当前 `mode=correct` 支持字段更正，但用户不知道有这个能力。

处理：在预览卡片上直接提供「修改金额」这类快捷入口，把纠错从"再打一句话"降级为"点一下改一个字段"。这类入口对降低误操作率比优化话术更有效。

### 14.7 等待期间没有进度

模型响应通常一两秒，超时为十五秒。这段时间界面只有「处理中」，用户无法判断是在思考还是已经卡住。

处理：超过两秒推送一条进度事件，例如「正在核对学生与课程」，让等待可感知。

### 14.8 移动端

响应式断点已存在，但多尺寸视觉矩阵与深链未验收，属于既有 P2 范围。本轮不扩展，但需要在新设计中保留这条已知限制，避免重构后被误认为已覆盖。

## 15. 实施记录（2026-10-28）

本轮已落地并实测，与设计稿的偏差如实列出。

### 15.1 已完成

| 项 | 落地位置 | 说明 |
|---|---|---|
| 意图层单一入口 | `apps/agent-runtime/src/graph/intent-parser.ts` | 模型为唯一入口；输出不合约定时纠错一次，仍失败降级为澄清提问而不是让 run 失败；模型不可用时返回明确降级态 |
| 规则退居影子 | 同上 `shadowRules` | 默认开启但只做对照记录，不参与决策；`AGENT_INTENT_RULE_FALLBACK=true` 可随时恢复为兜底 |
| Core 拒绝原因 | `apps/core-api/src/common/errors/business-reason.filter.ts` | 全局过滤器为 403/409 附加 `code`，抛错点与异常类型未改动，现有测试零影响 |

| 对话链路去图 | `dialogue-graph.ts` 的 `runTurn` | 移除 StateGraph，改为顺序执行加载上下文、理解、执行三步；`createDialogueGraph` 保留门面，`invoke` 签名不变，现有测试无需改写 |
| 做不到的请求给替代路径 | `intent-parser` 提示词 + `dialogue-graph` unsupported 分支 | 模型输出 `unsupported` 并可携带 `question`，回答时优先展示该引导，取代原来的一句通用兜底 |
| 测评套件 | `apps/agent-runtime/eval/` | 72 条基线语料、评估运行器、Markdown 报告；累计三轮调优后 72/72 通过 |
| 姓名脱敏 | `apps/agent-runtime/src/graph/privacy-mask.ts` | 发送前把已知学生、教师、课程名替换为「实体1」这类占位符，模型返回后精确还原；脱敏后评估仍为 72/72 |

### 15.2 与设计的偏差

**业务语义守卫保留。** 设计稿第 5 节称这些规则可以删除，因为 Core 会兜底。实测后修正判断：退款手续费不得重复登记、不得跨课程抵扣欠费、不得通过改日期绕过关账，这三类判断依赖用户原话的语义，Core 只拿到结构化参数，无法识别。删除会真实造成错误入账。现已明确它们不是意图识别，而是 Plan 层的语义守卫，不参与 operation 判定，也不影响模型识别能力。

**LangGraph 依赖未从依赖清单移除。** 对话主链路已完全不使用 `StateGraph`，但 `business-query-graph` 与 `spike-graph` 仍在引用，故 `package.json` 保留依赖。若后续确认这两处也被 pipeline 取代，再统一移除。

**未建 `intent_audit` 表。** 评估改为离线语料加诊断回调，指标体现在评估报告而非运行期表。运行期只保留 `AGENT_INTENT_DIAGNOSTICS=true` 时的结构化日志。

### 15.3 测评发现并已修复的设计缺口

| 缺口 | 后果 | 修复 |
|---|---|---|
| `DialogueIntentSchema` 把 `question`、`fields`、`operation` 视为必填 | 模型省略 `question` 时，13 条用例被判为"输出不合法" | 三者加默认值，缺失即视为 null 或空对象 |
| 学生电话未进入意图字段契约 | 「把电话改成…」被判为不支持，而 Core 早已支持 | `phone` 补入字段表与学生新增/修改契约，并透传到预览命令 |
| `unsupported` 只返回通用兜底 | 用户说了明确诉求却被回「请说明要办哪一项」 | 允许模型在 `unsupported` 时携带建议，回答优先展示 |

第二项属于典型的契约漂移：Core 加了字段，意图层没同步。这类问题靠人工审查很难发现，是测评套件的直接收益。

### 15.4 尚未实施

第 13 节剩余两项待落地：同会话并发互斥、取消范围与多步事务的表述规则。两者都不改动架构，可独立交付。

脱敏的已知边界：只有已经从 Core 候选列表里拿到姓名的对象会被替换，用户首次提到的新名字仍以原文发送。要完整覆盖，需产品先确认第三方模型的数据条款。

## 16. 待评审决策

以下三点需要明确，否则实施会走偏。

第一，LangGraph 是保留并真正用起来（interrupt + 多节点拆分），还是彻底移除。我倾向前者只在"确认环节断点"有价值时保留，否则移除更干净。

第二，回答文本是否完全模板化。若产品上要求"更像人说话"，可以保留模型润色，但必须限制在无数字场景，并且要把误伤检查改成"仅在出现第一人称施事句式时拦截"。

第三，阶段二要求 Core 新增拒绝原因字段，这属于 Core 接口变更，需要确认是否接受在 MVP 阶段引入。
